## 2. 技术目标

本方案围绕以下目标设计：

- 用最小但可扩展的架构，先完成 V1 功能闭环
- 优先发挥 Next.js 的静态化与缓存能力，降低数据库访问和图片生成成本
- 确保“全站同一天同一条内容”的业务规则可以稳定落地
- 将 AI 图片生成设计为“低频、可审核、可替换”的后台流程，而不是前台实时计算
- 为后续接入轻量后台、统计、广告和多时区展示保留演进空间

## 3. 已确认技术决策

- 包管理：`pnpm`
- 前端框架：`Next.js`
- 语言：`TypeScript`
- 数据库主方案：`Postgres`
- ORM：`Drizzle ORM`
- 本地快速验证：不把 `DuckDB` 作为主站数据库；如后续需要，可仅用于离线分析或批处理工具
- 部署取向：以 `Vercel` 为主方案，文档中允许保留 `Netlify` 可适配说明
- 公开页面渲染策略：静态优先 + 定时失效
- 内容事实源：数据库为准
- 图片资源存储：对象存储，优先 `Cloudflare R2`
- 后台鉴权：单管理员账号密码登录
- AI 提示词来源：内容库预置 prompt
- 内容建模：三表主拆分
- 图片生成触发：定时任务
- 审核时序：提前一天生成并审核次日内容

## 4. 推荐技术栈

### 4.1 应用层

- `Next.js App Router`
- `React Server Components`
- `TypeScript`
- `pnpm`

推荐原因：

- App Router 更适合内容站、静态化页面、路由级缓存和 `metadata`
- Server Components 更适合数据库读取、SEO 页面输出和减少客户端 JS
- Next.js 原生支持 `revalidate`、按路径刷新和图片相关能力，适合本项目“公开内容静态、后台操作动态”的结构

### 4.2 数据层

- 生产数据库：`Postgres 16`
- 开发数据库：同样推荐 `Postgres 16`
- ORM：`Drizzle ORM`
- 数据迁移：`drizzle-kit`

推荐原因：

- 本项目需要稳定的内容表、发布记录、后台登录和生成任务状态，`Postgres` 比 `DuckDB` 更适合作为应用数据库
- `Drizzle + Postgres` 的开发体验、类型安全和迁移能力较成熟
- 开发与生产尽量同构，可以减少后期从本地验证切到线上数据库时的差异成本

### 4.3 存储层

- 对象存储：`Cloudflare R2`
- 存储内容：
  - 原始 AI 背景图
  - 已排版完成的分享卡片图
  - 可选的缩略图或预览图

推荐原因：

- 图片资源适合单独走对象存储和 CDN
- R2 成本友好，适合未来图片数量增长
- 公开资源 URL 可以稳定服务于站内页面、Open Graph 预览和社交分享

### 4.4 认证层

- 后台采用单管理员登录
- 第一版推荐用最简单的账号密码方案
- 技术实现可使用基于 session 的轻量认证方案

推荐原因：

- 当前只有一个管理员，不需要引入复杂的多租户或组织权限模型
- 账号密码登录不依赖邮件系统，比 magic link 更适合 V1

## 6. 本地开发环境建议

### 6.1 本地数据库

推荐你在本地安装：

- `Postgres 16.x`

不建议当前阶段把本地主数据库设为 DuckDB，原因如下：

- `Drizzle` 与 `Postgres` 的组合最顺
- 你后续会有后台、任务状态、内容审核、发布记录，这些都更适合关系型 OLTP 数据库
- DuckDB 更适合分析和离线处理，而不是站点主业务数据库

### 6.2 安装建议

macOS 下推荐两种方式：

- `Postgres.app`
  - 优点：安装最简单，适合前端背景开发者
  - 建议版本：选择 `Postgres 16`
- `Homebrew`
  - 适合你希望命令行管理服务
  - 建议版本：`postgresql@16`

推荐优先级：

- 第一推荐：`Postgres.app 16`
- 第二推荐：`Homebrew + postgresql@16`

### 6.3 本地数据库命名建议

- 数据库名：`bible_verse`
- 本地连接用户：使用本机默认用户即可
- ORM 连接串统一通过环境变量管理

## 7. 系统架构总览

整体采用“三层结构”：

- `Next.js Web App`
  - 负责公开页面、后台页面、路由、缓存、SEO、表单操作
- `Postgres`
  - 负责内容主数据、生成记录、发布记录、管理员数据
- `R2`
  - 负责图片文件存储与公开访问

后台任务采用“应用内任务入口 + 平台定时触发”的方式：

- 每天定时触发生成次日候选内容
- 生成结果写入数据库
- 图片上传到 R2
- 管理后台进行人工确认
- 审核通过后，该条记录进入正式发布状态

## 8. 核心业务流程

### 8.1 内容生命周期

建议把一条内容的生命周期拆成四个阶段：

1. 内容入库
2. 候选生成
3. 人工审核
4. 正式发布

### 8.2 每日生成与发布流程

推荐流程如下：

1. 系统每天提前一天，在固定时间运行定时任务
2. 任务根据美国东部时间找到“次日要发布的日期”
3. 从内容表中选出一条近三个月未使用、状态可用的经文
4. 读取该条内容的预置 prompt
5. 调用 AI 图片 provider 生成背景图
6. 生成成功后，把原图上传到 R2
7. 在服务端组合生成两张卡片图：
   - 简洁版：经文 + 出处
   - 扩展版：经文 + 出处 + 解释
8. 将卡片图上传到 R2
9. 写入生成任务记录，状态变为待审核
10. 管理员进入后台审核
11. 审核通过后，写入发布记录或将发布状态标记为已批准
12. 到达目标日期后，公开站点只读取“该日期已批准的唯一发布记录”

### 8.3 替换流程

后台需要支持“重新生成替换”：

1. 管理员打开某天候选内容
2. 点击“重新生成”
3. 系统创建新的生成任务记录
4. 保留旧记录，但将新记录作为当前候选
5. 管理员审核后确认最终发布版本

这样做的好处：

- 不丢失历史生成记录
- 可以比较不同图片版本
- 后续可统计哪个 prompt 或 provider 效果更好

## 10. 为什么采用“三表主拆分”

你提到“生成好的摘抄怎么储存、怎么建表”，这里给出明确建议：

- `verses` 负责“内容本体”
- `image_generations` 负责“生成过程和图片资产”
- `daily_publications` 负责“某天最终发布结果”

不要把三者揉成一张表，原因如下：

- 一条经文可以多次生成不同图片
- 同一天的候选可以被替换
- 发布状态与图片生成状态不是同一个概念
- 后续做后台、审计、统计时，拆分模型更清楚

简单理解：

- 内容表回答“有什么内容”
- 生成表回答“这条内容生成过哪些图片”
- 发布表回答“某天最终上线的是哪个版本”

## 11. 推荐缓存策略

这是本项目最关键的技术设计点之一。

### 11.1 缓存原则

- 公开页面尽量静态化
- 后台页面保持动态
- 图片生成绝不发生在公开访问链路中
- 页面更新依赖“按路径刷新 + 定时失效”，而不是每次请求都查询实时状态

### 11.2 页面缓存策略

#### 首页

- 使用静态生成
- 设置 `revalidate`，建议按小时级或更短周期兜底
- 当某日内容审核通过或替换时，主动触发首页的按路径刷新

首页读取逻辑：

- 只读取“今天已发布的唯一记录”
- 如果今天尚未到发布时间但内容已批准，也不提前公开

#### 详情页

- 使用静态生成
- 基于已发布内容生成详情页
- 审核通过或替换图片后，对对应详情页执行按路径刷新

#### 归档页

- 使用静态生成
- 通过 `revalidate` + 每次发布后主动刷新

### 11.3 数据缓存策略

- 公开页面的数据查询走服务端
- 对外公开查询尽量只查发布表和必要关联字段
- 后台查询不做激进缓存，优先保证一致性

### 11.4 图片缓存策略

- AI 背景图与卡片图一旦生成完成，就作为静态资产长期缓存
- 图片 URL 应具备版本性或唯一文件名，避免替换后 CDN 命中旧图

推荐命名方式：

- `/cards/2026-05-01/generation-3-simple.png`
- `/cards/2026-05-01/generation-3-extended.png`

### 11.5 为什么这套策略省成本

- 同一天全站只展示一条内容，所以当天只需生成一次候选图片集
- 公开访问不会触发 AI 调用
- 页面大部分请求命中静态缓存
- 替换图片时只重刷相关路径，不影响整站

## 13. AI Provider 抽象建议

你已经确认要抽象 provider 层，这个决定是正确的。

推荐接口职责：

- 输入：
  - prompt
  - 风格配置
  - 宽高比
- 输出：
  - 原始图 URL 或二进制
  - provider 请求 ID
  - 错误信息

第一版只接一个实际 provider，但代码层预留如下能力：

- 更换 provider
- 更换模型
- 失败后重试
- 记录不同 provider 生成效果

为什么要抽象：

- 后续你可能因为成本、效果或审核要求更换服务商
- 统一接口后，后台和任务逻辑不需要跟着重写

## 14. 图片合成方案建议

图片合成建议在服务端完成，不放到浏览器端。

推荐原则：

- 原始背景图和最终卡片图分开存
- 卡片图生成时直接输出最终 PNG
- 简洁版和扩展版分别单独生成

服务端合成负责：

- 加载背景图
- 叠加遮罩或渐变，提升文字可读性
- 绘制经文正文
- 绘制出处
- 绘制解释文案

为什么不建议前台实时叠图：

- 会让社媒预览和分享图不稳定
- 会影响首屏性能
- 无法作为稳定的 OG 图资源复用

## 16. 定时任务设计建议

在 `Vercel` 取向下，推荐采用“平台 Cron 调一个内部安全接口”的模式。

建议任务类型：

- 每日候选生成任务
- 可选的过期清理任务

每日候选生成任务职责：

- 计算次日日期
- 查找是否已有有效候选
- 没有则自动选经文并生成
- 有则跳过，避免重复调用 AI

幂等性要求：

- 同一目标日期的生成任务不能重复制造多个“当前有效候选”
- 即使 Cron 重复触发，也不能无限重复调用 AI

建议通过以下机制实现：

- 发布日期唯一约束
- 状态检查
- 任务开始前先查库

## 17. 安全与权限建议

V1 只需要最小安全方案，但以下几点不能省：

- 后台路由必须鉴权
- 管理员密码必须哈希存储
- Cron 内部接口必须带服务端密钥
- 手动重新生成接口必须校验管理员权限
- R2 上传应使用服务端凭证，不能暴露到前端

## 18. SEO 与分享技术要点

由于这个站点高度依赖分享和搜索，技术上要特别注意：

- 首页和详情页都需要稳定 `metadata`
- 详情页的标题、描述、OG 图应来自该条已发布内容
- 分享 URL 必须指向详情页 canonical 地址
- 历史归档页需要可抓取、可分页扩展

图片方面：

- 建议 Open Graph 默认使用简洁版卡片图
- 页面正文中可以同时展示简洁版或扩展版，以后续 UI 设计为准

## 20. 技术风险与应对

### 20.1 图片生成成本失控

风险：

- Cron 或手动重试若无幂等控制，可能重复调用 AI

应对：

- 目标日期唯一约束
- 生成前查库
- 手动重生明确创建新版本并替代旧版本

### 20.2 发布时没有可用图片

风险：

- 次日内容未审核通过，可能导致当天无内容发布

应对：

- 提前一天生成并审核
- 后台突出“明日待审核”状态

### 20.3 缓存不一致

风险：

- 图片已替换但首页或详情页仍显示旧版本

应对：

- 发布/替换后执行按路径刷新
- 图片文件名版本化

### 20.4 表结构耦合过深

风险：

- 如果内容、生成、发布混成一表，后续难扩展

应对：

- 保持三表主拆分

## 21. 本方案的关键结论

- 用 `Next.js App Router + TypeScript + pnpm` 做公开站点和简易后台
- 用 `Postgres 16 + Drizzle` 作为唯一主业务数据库
- 用 `Cloudflare R2` 存储背景图与卡片图
- 用“内容表 + 生成任务表 + 发布记录表”作为核心业务模型
- 用“提前一天生成 + 人工审核 + 当天只读已发布记录”保证业务稳定
- 用“静态优先 + revalidate + 按路径刷新”实现高性能与低成本
- 不把 AI 生成放在公开访问链路里
- 不把 DuckDB 作为主站数据库，只保留为未来离线工具可选项
