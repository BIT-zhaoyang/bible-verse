# 网站架构设计模式

版本：2026-05-07

## 写在前面

很多人学习做网站时，会先学页面、组件、数据库、接口、部署。这样当然可以做出东西，但经常会遇到一个更深的问题：面对一个陌生网站，我应该如何拆解它？我要先设计页面，还是先设计数据表？我要先做用户系统，还是先做核心业务？为什么有些网站看起来只是几个页面，背后却需要审核、队列、权限、搜索、缓存和支付？

代码有设计模式，网站也有设计模式。只是网站设计模式不像 GoF 设计模式那样有一个广为统一的目录。它分散在产品设计、信息架构、数据库建模、后端架构、前端体验、运营增长和商业化方案之中。

这本小册把这些分散的经验整理成一套可复用的方法论。目标不是让你背诵所有网站类型，而是让你学会识别任何网站背后的结构：

```text
网站 = 用户角色 + 核心资源 + 操作行为 + 状态流转 + 权限边界 + 页面入口 + 后台流程 + 外部服务 + 增长路径 + 商业闭环
```

只要能拆出这些要素，你就能进一步判断：

- 这个网站属于哪种类型？
- 它的核心功能模块是什么？
- 每个模块有哪些常见解决方案？
- 哪些功能现在必须做，哪些可以以后做？
- 数据表应该如何组织？
- 哪些流程需要后台、队列、定时任务或第三方服务？

本小册可以作为你之后设计任何网站时的检查清单和模式库。

## 1. 网站架构的基本公式

初学者容易把网站理解为页面集合：

```text
首页 + 列表页 + 详情页 + 登录页 + 后台页 = 网站
```

这只是表面。页面是用户看到的结果，不是网站的本质。网站真正的本质是资源被不同角色以不同权限操作，并在一系列状态中流转。

更好的公式是：

```text
网站 = 角色 + 资源 + 行为 + 状态 + 权限 + 入口 + 流程
```

### 1.1 角色

角色是网站中的参与者。常见角色包括：

- 游客
- 注册用户
- 会员
- 管理员
- 内容编辑
- 商家
- 买家
- 老师
- 学生
- 审核员
- 组织管理员

设计网站时，不要只问“有没有用户系统”，而要问“有哪些角色？他们分别能做什么？”

例如内容网站中可能只有游客和管理员。电商网站中至少有游客、买家、商家、平台管理员。SaaS 网站中可能有个人用户、团队成员、团队管理员、系统管理员。

### 1.2 资源

资源是网站真正管理的东西。页面围绕资源展开，功能围绕资源发生。

常见资源包括：

- 文章
- 商品
- 订单
- 文件
- 图片
- 视频
- 用户
- 评论
- 课程
- 任务
- 项目
- 订阅
- 支付记录
- 通知

设计网站时，第一件重要的事是找出核心资源。

内容网站的核心资源是内容。电商网站的核心资源是商品和订单。工具网站的核心资源是用户提交的任务和生成结果。社区网站的核心资源是帖子、评论和关系链。

### 1.3 行为

行为是角色对资源做的动作。

常见行为包括：

- 创建
- 查看
- 编辑
- 删除
- 发布
- 审核
- 上传
- 下载
- 搜索
- 购买
- 支付
- 评论
- 点赞
- 收藏
- 分享
- 邀请

一个网站的功能清单，本质上就是“哪些角色可以对哪些资源执行哪些行为”。

### 1.4 状态

状态描述资源处在生命周期的哪个阶段。

例如文章可能有：

```text
draft -> review_required -> approved -> published -> archived
```

订单可能有：

```text
created -> paid -> fulfilled -> completed -> refunded
```

文件处理任务可能有：

```text
pending -> processing -> succeeded -> failed
```

只要一个资源不是一次性创建后永远不变，就很可能需要状态设计。状态设计清楚，网站就稳定；状态设计混乱，后续代码会迅速变成一团条件判断。

### 1.5 权限

权限决定谁可以做什么。

权限问题通常有三个层次：

- 你是谁：身份认证
- 你属于哪里：组织、团队、租户、项目
- 你能做什么：角色、权限、资源所有权

最简单的网站只有公开页面和管理员后台。复杂一些的网站会有会员内容、团队协作、多角色审批、组织隔离和细粒度权限。

### 1.6 入口

入口是用户接触资源的页面或界面。

常见入口包括：

- 首页
- 列表页
- 详情页
- 搜索页
- 分类页
- 个人中心
- 工作台
- 管理后台
- 分享落地页
- 邮件链接
- 第三方回调页

很多网站失败不是因为功能做少了，而是入口设计错了。用户不知道从哪里开始，也不知道下一步该做什么。

### 1.7 流程

流程是多个行为和状态串起来之后形成的业务链路。

例如内容发布流程：

```text
创建内容 -> 编辑内容 -> 预览 -> 提交审核 -> 审核通过 -> 定时发布 -> 展示给用户 -> 被分享 -> 带来访问
```

文件处理流程：

```text
上传文件 -> 校验文件 -> 创建任务 -> 后台处理 -> 存储结果 -> 通知用户 -> 下载结果
```

电商下单流程：

```text
浏览商品 -> 加入购物车 -> 结算 -> 支付 -> 生成订单 -> 发货 -> 确认收货 -> 评价
```

一个网站的架构设计，就是把这些流程拆成稳定、可维护、可扩展的模块。

## 2. 网站设计模式是什么

网站设计模式不是一种神秘概念。它是对反复出现的问题和解决方案的总结。

一个模式通常回答五个问题：

```text
问题：这个模式解决什么问题？
场景：什么时候会遇到这个问题？
方案：通常如何设计？
代价：这个方案有什么成本和限制？
检查：实现时要注意什么？
```

例如“文件上传与对象存储”就是一个模式。

问题：用户或系统需要保存图片、视频、文档、生成物。

场景：头像上传、商品图片、文章封面、AI 生成图片、PDF 转换结果。

方案：文件放对象存储，数据库只存元数据和 URL；公开文件走 CDN，私有文件走签名 URL。

代价：需要处理上传失败、权限、文件大小、病毒扫描、过期清理和费用。

检查：文件是否校验？URL 是否可访问？是否区分公开和私有？是否有清理机制？

这就是网站设计模式。

### 2.1 模式不是模板

模式不是固定模板。不是说所有内容网站都必须有评论，所有 SaaS 都必须有团队空间，所有工具站都必须有支付。

模式的意义是帮助你识别“这里可能有一个成熟问题”，然后选择合适的解法。

### 2.2 模式的三个层级

网站设计模式可以分为三个层级。

第一层是网站类型模式：

- 内容型网站
- 工具型网站
- 电商网站
- SaaS 网站
- 社区网站
- Marketplace 平台

第二层是功能模块模式：

- 登录
- 上传
- 搜索
- 支付
- 评论
- 审核
- 通知
- 订阅

第三层是系统实现模式：

- SSR
- 静态生成
- API 服务
- 数据库
- 对象存储
- 队列
- 缓存
- 搜索索引
- Webhook

真正的网站架构设计，就是把这三层组合起来。

### 2.3 你要建立自己的模式库

当你看一个网站时，可以尝试把它翻译成模式组合：

```text
Notion = SaaS + 工作区 + 文档资源 + 权限 + 协作 + 搜索 + 订阅
Shopify 店铺 = 电商 + 商品目录 + 购物车 + 支付 + 订单 + 库存 + 后台
Substack = 内容站 + 邮件订阅 + 会员付费 + 作者后台 + SEO
图片压缩工具 = 工具站 + 文件上传 + 异步处理 + 结果下载 + 额度限制
```

当你能这样拆解网站时，你就不再是“凭感觉做页面”，而是在做架构设计。

## 3. 拆解任何网站的十个问题

面对一个新网站，不要从技术栈开始。先问十个问题。

### 3.1 这个网站服务谁？

列出所有用户角色。

例子：

```text
游客：浏览公开内容
注册用户：收藏、评论、订阅
作者：创建和管理内容
管理员：审核和配置网站
```

### 3.2 用户来这里完成什么任务？

用户任务比功能名称更重要。

不要只写“搜索功能”，要写“用户需要快速找到某个主题下的历史文章”。不要只写“上传功能”，要写“用户需要上传原文件，并在处理完成后下载结果”。

### 3.3 核心资源是什么？

如果只能保留一个数据对象，这个网站最不能丢的是什么？

内容站是文章。电商是商品和订单。SaaS 是用户的业务数据。工具站是任务和结果。社区是帖子和互动。

### 3.4 资源从哪里来？

资源可能来自：

- 管理员手工创建
- 用户提交
- 第三方 API 同步
- AI 生成
- 定时任务生成
- 批量导入
- 爬虫采集

来源不同，架构也不同。用户提交需要审核和风控。AI 生成需要任务状态和失败重试。第三方同步需要 Webhook 或定时拉取。

### 3.5 谁能修改资源？

修改权限决定后台和权限模型。

例如商品可以由商家修改，但平台管理员可以下架。文章可以由作者编辑，但编辑审核后才能发布。订单不能随便修改，只能通过支付、退款、发货等动作改变状态。

### 3.6 资源有哪些生命周期？

为每个核心资源写出状态流转。

例如：

```text
Article: draft -> review -> published -> archived
Order: created -> paid -> shipped -> completed -> refunded
UploadJob: pending -> processing -> succeeded -> failed
Subscription: trialing -> active -> past_due -> canceled
```

### 3.7 用户从哪里进入？

入口包括搜索引擎、社交分享、广告、首页、邮件、后台、第三方回调。

不同入口决定页面设计重点。

搜索入口需要 SEO。社交入口需要分享预览。邮件入口需要明确落点。后台入口需要高效操作。

### 3.8 哪些流程需要后台？

后台不是只有管理员页面。只要有运营、审核、配置、数据修复、任务追踪，就需要后台能力。

常见后台功能包括：

- 内容管理
- 用户管理
- 审核队列
- 订单管理
- 文件管理
- 系统配置
- 数据统计
- 任务日志
- 失败重试

### 3.9 哪些事情不能同步完成？

如果一个动作耗时长、容易失败、依赖第三方或需要重试，就应该考虑异步。

常见异步任务包括：

- 图片生成
- 视频转码
- 邮件发送
- 支付回调处理
- 数据导入
- 搜索索引更新
- 报表生成
- 批量通知

### 3.10 网站靠什么增长和变现？

增长和变现会影响架构。

内容站重视 SEO、分享和订阅。SaaS 重视注册转化、试用、付费和留存。电商重视商品曝光、转化率、复购和物流体验。社区重视内容生产、互动和召回。

如果一开始完全不考虑增长路径，后面经常会补埋点、补 SEO、补分享、补邮件系统，成本更高。

## 4. 网站的十种常见类型

本章先给出大类。后面会讲每类如何组合功能模式。

### 4.1 内容型网站

典型例子：博客、新闻站、教程站、灵修网站、菜谱站、评测站。

核心资源：

- 文章
- 图片
- 分类
- 标签
- 作者

常见功能：

- 首页
- 列表页
- 详情页
- 分类页
- 标签页
- 搜索
- 归档
- 分享
- SEO
- 订阅
- CMS 后台

核心架构：

```text
内容创建 -> 审核/编辑 -> 发布 -> 页面展示 -> SEO 收录 -> 分享传播 -> 订阅召回
```

### 4.2 工具型网站

典型例子：图片压缩、PDF 转换、二维码生成、AI 写作、AI 图片生成。

核心资源：

- 输入
- 任务
- 结果
- 文件
- 使用额度

常见功能：

- 表单输入
- 文件上传
- 参数配置
- 任务处理
- 进度状态
- 结果预览
- 下载
- 历史记录
- 额度限制
- 付费升级

核心架构：

```text
用户输入 -> 创建任务 -> 后台处理 -> 结果存储 -> 展示/下载 -> 记录用量
```

### 4.3 电商网站

典型例子：品牌独立站、商城、数字商品销售网站。

核心资源：

- 商品
- SKU
- 库存
- 购物车
- 订单
- 支付
- 物流

常见功能：

- 商品列表
- 商品详情
- 搜索筛选
- 购物车
- 结算
- 支付
- 优惠券
- 订单管理
- 物流跟踪
- 售后退款
- 评价

核心架构：

```text
商品曝光 -> 加购 -> 结算 -> 支付 -> 生成订单 -> 履约 -> 售后 -> 复购
```

### 4.4 SaaS 网站

核心资源：

- 用户
- 组织
- 工作区
- 项目
- 业务对象
- 权限
- 订阅

常见功能：

- 注册登录
- 工作区
- 数据 CRUD
- 团队成员
- 角色权限
- 设置
- 邀请
- 订阅计费
- 数据导入导出
- 审计日志

核心架构：

```text
注册 -> 创建工作区 -> 创建业务数据 -> 协作 -> 权限控制 -> 计费 -> 留存
```

### 4.5 社区网站

核心资源：

- 用户
- 帖子
- 评论
- 点赞
- 收藏
- 关注关系
- 通知

常见功能：

- 发帖
- 评论
- 点赞

```text
访客进入 -> 理解价值 -> 建立信任 -> 提交线索 -> 销售跟进
```

### 4.10 内部后台系统

典型例子：CMS、运营后台、客服系统、审核后台。

核心资源：

- 业务数据
- 操作记录
- 配置
- 权限
- 审核任务

常见功能：

- 登录
- 数据列表
- 筛选
- 编辑
- 批量操作
- 审核
- 导入导出
- 权限
- 日志
- 报表

核心架构：

```text
管理员登录 -> 查找数据 -> 执行业务动作 -> 记录日志 -> 影响前台或业务流程
```

## 5. 通用模式一：资源与 CRUD

### 5.1 问题

几乎所有网站都要管理某种资源。资源需要创建、查看、编辑、删除，也就是 CRUD。

但真正的问题不是“如何写增删改查”，而是：

- 这个资源是否公开？
- 谁可以创建？
- 谁可以编辑？
- 删除是真删还是软删？
- 是否需要状态？
- 是否需要版本？
- 是否需要审核？
- 是否需要归属到用户、组织或项目？

### 5.2 常见方案

最简单的资源表：

```text
id
title
body
created_at
updated_at
```

稍完整的资源表：

```text
id
owner_id
title
body
status
created_at
updated_at
published_at
deleted_at
```

如果是多租户 SaaS，通常还需要：

```text
workspace_id
created_by
updated_by
```

### 5.3 页面模式

资源通常对应这些页面：

- 列表页
- 新建页
- 编辑页
- 详情页
- 删除确认
- 空状态

后台资源管理还会增加：

- 筛选
- 排序
- 批量操作
- 导入导出
- 操作日志

### 5.4 常见坑

第一，过早删除数据。很多业务数据不应该物理删除，而应该软删除或归档。

第二，没有状态字段。后续要加草稿、审核、禁用时会很痛苦。

第三，没有所有者字段。后续做权限时无法判断数据归属。

第四，把所有东西塞进一个大表。短期快，长期难维护。

### 5.5 检查清单

- 是否定义了资源所有者？
- 是否需要状态字段？
- 是否需要软删除？
- 是否需要公开 URL 或 slug？
- 是否需要创建者和更新者？
- 是否需要版本管理？
- 是否需要审核记录？
- 是否需要批量操作？

## 6. 通用模式二：用户、身份与权限

### 6.1 问题

当网站需要区分“谁在操作”时，就需要身份系统。当不同人能做的事情不一样时，就需要权限系统。

### 6.2 身份模式

常见身份模式有四种。

第一种是无登录网站。适合纯公开内容站、落地页、小工具。

第二种是管理员登录。适合有公开前台和内部后台的网站。

第三种是普通用户登录。适合收藏、订单、历史记录、个人数据。

第四种是组织和团队登录。适合 SaaS、企业协作、多人管理后台。

### 6.3 会话方案

常见会话方案：

- Cookie Session
- JWT
- OAuth
- Magic Link
- 第三方登录

对于普通网站，Cookie Session 通常简单可靠。对于跨端 API 或移动端，Token 方案更常见。对于企业级登录，OAuth、OIDC、SAML 会出现。

### 6.4 权限模型

最常见的权限模型有三类。

角色权限：

```text
admin
editor
member
viewer
```

资源所有权：

```text
用户只能编辑自己创建的内容
团队成员只能访问所在工作区的数据
```

能力权限：

```text
can_publish_article
can_manage_billing
can_invite_member
```

简单网站用角色就够。复杂 SaaS 通常需要角色加资源所有权。企业后台可能需要能力权限。

### 6.5 常见坑

第一，把“登录了”当成“有权限”。登录只证明身份，不证明权限。

第二，在前端隐藏按钮，但后端不校验。权限必须在服务端校验。

第三，没有考虑资源归属。用户 A 登录后不能访问用户 B 的数据。

第四，后台所有管理员都是超级管理员。早期可以这样，但后期会有运营风险。

### 6.6 检查清单

- 哪些页面公开？
- 哪些页面需要登录？
- 哪些操作需要管理员？
- 数据是否归属于用户、组织或项目？
- 权限是在服务端校验的吗？
- 是否有会话过期？
- 是否有退出登录？
- 是否需要操作日志？

## 7. 通用模式三：内容管理与发布

### 7.1 问题

内容型网站的核心是稳定地产生、管理、发布和传播内容。

内容管理不只是“文章表”。它通常包括：

- 内容池
- 草稿
- 编辑
- 审核
- 定时发布
- 归档
- SEO
- 分享预览
- 作者和分类

### 7.2 基础内容模型

一篇内容通常需要：

```text
id
slug
title
summary
body
cover_image_url
status
author_id
published_at
created_at
updated_at
```

如果面向 SEO，最好有：

```text
seo_title
seo_description
canonical_url
og_image_url
```

如果需要分类和标签：

```text
categories
tags
```

### 7.3 内容状态

常见状态流转：

```text
draft -> review_required -> approved -> scheduled -> published -> archived
```

简单网站可以只有：

```text
draft -> published
```

但一旦有多人协作、AI 生成或运营审核，就应该明确状态。

### 7.4 页面模式

内容站常见页面：

- 首页
- 内容列表
- 内容详情
- 分类页
- 标签页
- 作者页
- 归档页
- 搜索页
- 关于页

后台常见页面：

- 内容列表
- 新建内容
- 编辑内容
- 预览
- 审核队列
- 发布排期
- 媒体库

### 7.5 架构模式

内容发布链路通常是：

```text
内容源 -> 内容库 -> 审核/编辑 -> 发布记录 -> 前台页面 -> SEO/分享 -> 统计反馈
```

如果内容由 AI 生成，则变成：

```text
Prompt/素材 -> AI 生成 -> 存储结果 -> 人工审核 -> 发布 -> 反馈
```

### 7.6 常见坑

第一，没有独立详情页。内容无法被搜索引擎长期收录，也不利于分享。

第二，只把内容存在代码里。短期可以，长期运营困难。

第三，不做发布状态。后台一保存，前台立刻变化，容易误发布。

第四，不重视 slug 和 SEO 元数据。后期补 SEO 很麻烦。

### 7.7 检查清单

- 是否有内容详情页？
- 是否有稳定 slug？
- 是否区分草稿和已发布？
- 是否需要人工审核？
- 是否需要定时发布？
- 是否有 SEO 标题和描述？
- 是否有 Open Graph 分享图？
- 是否有归档和分类？

## 8. 通用模式四：文件上传与对象存储

### 8.1 问题

网站经常需要处理文件：头像、封面图、商品图、附件、视频、音频、AI 生成图片、转换后的 PDF。

文件不适合直接存在数据库里。通常做法是文件放对象存储，数据库保存元数据和访问地址。

### 8.2 基础架构

典型架构：

```text
浏览器/服务器 -> 上传文件 -> 对象存储 -> 返回 URL -> 数据库存元数据
```

常见对象存储：

- S3
- Cloudflare R2
- Google Cloud Storage
- Azure Blob Storage
- 本地文件系统

### 8.3 上传方案

服务器中转上传：

```text
浏览器 -> 应用服务器 -> 对象存储
```

优点是权限简单，服务端容易校验。缺点是服务器带宽压力大。

浏览器直传：

```text
浏览器 -> 获取签名上传 URL -> 直接上传对象存储 -> 回传文件信息
```

优点是性能好，适合大文件。缺点是实现复杂，需要签名 URL 和回调确认。

系统生成后上传：

```text
后台任务 -> 生成文件 -> 上传对象存储 -> 保存 URL
```

适合 AI 图片、报表、转码结果。

### 8.4 公开文件和私有文件

公开文件可以直接用 URL 访问，适合文章封面、商品图片、分享图。

私有文件不能直接公开访问，适合合同、发票、用户私密文档。通常用签名 URL 临时授权。

### 8.5 文件元数据

推荐为文件建立元数据表：

```text
id
owner_id
storage_provider
bucket
key
public_url
content_type
size
width
height
status
created_at
```

简单网站可以把 URL 直接存在业务表里。复杂网站最好抽象成文件表或媒体库。

### 8.6 常见坑

第一，只存 URL，不存 key。后续删除、迁移、重新生成会困难。

第二，不限制文件大小和类型。容易出现安全和成本问题。

第三，不区分公开和私有。可能泄露用户文件。

第四，不处理失败状态。数据库保存了 URL，但文件实际不存在。

第五，没有清理机制。临时文件和失败任务会长期占空间。

### 8.7 检查清单

- 文件是用户上传还是系统生成？
- 文件公开还是私有？
- 是否限制大小和类型？
- 是否需要图片尺寸和格式校验？
- 是否需要 CDN？
- 是否需要删除和清理？
- 是否保存 storage key？
- 是否有上传失败重试？

## 9. 通用模式五：搜索、筛选与发现

### 9.1 问题

当资源数量变多，用户需要找到特定内容。搜索和筛选就是发现系统。

### 9.2 三种常见方案

第一种是数据库查询。适合小规模、简单筛选。

例如：

```text
按分类筛选
按状态筛选
按创建时间排序
按标题模糊匹配
```

第二种是全文搜索。适合文章、文档、商品说明。

常见方案：

- PostgreSQL full-text search
- Meilisearch
- Typesense
- Elasticsearch
- OpenSearch

第三种是推荐系统。适合内容流、电商、社区、媒体站。早期可以用规则推荐，后期再做个性化。

### 9.3 搜索页面模式

常见搜索页面包括：

- 搜索输入框
- 筛选条件
- 排序
- 结果列表
- 高亮匹配
- 空结果
- 分页或无限加载

### 9.4 筛选模式

常见筛选维度：

- 分类
- 标签
- 时间
- 价格
- 状态
- 作者
- 地区
- 评分
- 文件类型

### 9.5 常见坑

第一，数据少时过早引入复杂搜索引擎。会增加维护成本。

第二，没有空结果设计。用户不知道下一步该怎么办。

第三，筛选状态不能分享。URL 中应该保存关键词和筛选参数。

第四，搜索索引和数据库不同步。

### 9.6 检查清单

- 数据量是否真的需要搜索引擎？
- 搜索目标是标题、正文、标签还是全部？
- 筛选条件是否可组合？
- 搜索 URL 是否可分享？
- 是否有空结果页？
- 是否需要搜索日志？
- 索引如何更新？

## 10. 通用模式六：状态机、审核与工作流

### 10.1 问题

很多网站的业务不是简单保存数据，而是让资源在多个状态之间流转。

例如：

- 内容需要审核后发布
- 商品需要上架和下架
- 订单需要支付和发货
- AI 生成结果需要人工确认
- 用户提交内容需要风控

### 10.2 状态机思维

状态机回答三个问题：

```text
有哪些状态？
哪些动作会改变状态？
谁能执行这些动作？
```

例如内容审核：

```text
状态：draft, review_required, approved, published, rejected
动作：submit, approve, reject, publish, archive
权限：作者可提交，编辑可审核，管理员可发布
```

### 10.3 审核队列模式

审核队列通常包括：

- 待审核列表
- 详情预览
- 通过
- 拒绝
- 修改建议
- 重新生成或重新提交
- 审核记录

### 10.4 工作流表设计

简单做法是在业务表里放 status。

复杂做法增加事件表：

```text
id
resource_type
resource_id
from_status
to_status
action
actor_id
reason
created_at
```

事件表的好处是可追踪、可审计、可回放。

### 10.5 常见坑

第一，状态定义含混。例如 approved 和 published 混在一起。

第二，允许非法状态跳转。例如未支付订单直接发货。

第三，没有记录谁做了什么。后续出现问题无法追责。

第四，审核和发布耦合。审核通过不一定意味着立刻发布。

### 10.6 检查清单

- 是否列出了所有状态？
- 是否列出了所有状态跳转？
- 是否限制非法跳转？
- 是否记录操作者？
- 是否记录原因？
- 是否需要撤回、回滚或重新提交？
- 是否需要定时发布？

## 11. 通用模式七：异步任务、队列与定时任务

### 11.1 问题

有些事情不适合在用户请求中立刻完成。

原因可能是：

- 耗时长
- 容易失败
- 需要调用第三方
- 需要重试
- 需要批量执行
- 不需要用户等待

### 11.2 常见异步任务

- AI 生成图片
- 视频转码
- 文件格式转换
- 邮件发送
- 数据导入
- 报表生成
- 搜索索引更新
- 支付回调处理
- 定时发布

### 11.3 基础任务模型

任务表通常包含：

```text
id
type
status
input
result
error_message
retry_count
scheduled_at
started_at
finished_at
created_at
updated_at
```

常见状态：

```text
pending -> processing -> succeeded
pending -> processing -> failed
failed -> pending
```

### 11.4 队列模式

队列适合处理大量异步任务。

典型流程：

```text
用户提交 -> 创建任务 -> 放入队列 -> Worker 处理 -> 更新结果 -> 通知用户
```

早期项目可以先用数据库任务表加定时轮询。业务增长后再引入专门队列。

### 11.5 定时任务模式

定时任务适合：

- 每天发布内容
- 每小时同步数据
- 每月生成账单
- 定期清理过期文件
- 定期发送邮件

定时任务要注意幂等性。也就是说，同一个任务重复执行，不应该产生错误的重复结果。

### 11.6 常见坑

第一，在网页请求中直接做耗时任务，导致超时。

第二，没有任务状态，失败后不知道发生了什么。

第三，没有重试机制。

第四，任务不是幂等的，重复执行会创建重复数据。

第五，没有后台查看任务。

### 11.7 检查清单

- 这个动作是否可能超过几秒？
- 是否依赖第三方服务？
- 是否需要重试？
- 是否需要任务状态？
- 是否需要后台查看？
- 是否需要取消任务？
- 是否需要定时执行？
- 是否幂等？

## 12. 通用模式八：支付、订阅与权益

### 12.1 问题

当网站要收费时，支付只是开始。真正复杂的是支付之后用户拥有什么权益。

### 12.2 支付类型

常见收费模式：

- 一次性购买
- 订阅
- 按量计费
- 充值余额
- 会员等级
- 平台抽佣

### 12.3 核心资源

支付系统通常涉及：

```text
Customer
Product
Price
Order
Payment
Subscription
Entitlement
Invoice
WebhookEvent
```

### 12.4 Webhook 模式

支付平台通常通过 Webhook 通知你支付结果。

典型流程：

```text
创建支付会话 -> 用户付款 -> 支付平台发送 Webhook -> 服务端验证签名 -> 更新订单/订阅 -> 开通权益
```

关键点：不要只相信前端跳转成功页。真正的支付状态应该以服务端 Webhook 为准。

### 12.5 权益模式

权益决定用户能用什么。

例如：

- 每月可生成 100 张图片
- 可创建 3 个项目
- 可访问付费文章
- 可邀请 10 个成员
- 可导出高清文件

权益通常需要和套餐、订阅状态、用量记录关联。

### 12.6 常见坑

第一，把支付成功和权益开通写在前端回调里。用户可能绕过或刷新失败。

第二，没有处理订阅取消、支付失败、退款。

第三，没有记录 Webhook 事件，重复通知时无法幂等处理。

第四，没有单独的权益判断层，导致付费逻辑散落在代码各处。

### 12.7 检查清单

- 收费模式是什么？
- 支付成功以什么为准？
- 是否有 Webhook 验签？
- 是否记录支付事件？
- 是否处理退款？
- 是否处理订阅过期？
- 权益如何判断？
- 用量如何记录？

## 13. 通用模式九：通知、邮件与用户召回

### 13.1 问题

网站不只是等用户访问，也需要在合适的时候主动触达用户。

### 13.2 通知类型

常见通知包括：

- 注册验证
- 密码重置
- 任务完成
- 支付成功
- 订单状态变化
- 评论回复
- 每日内容推送
- 营销邮件
- 系统告警

### 13.3 通知渠道

常见渠道：

- 邮件
- 站内通知
- 浏览器推送
- 短信
- Webhook
- Slack 或企业微信

### 13.4 通知架构

推荐把通知做成独立事件。

```text
业务事件 -> 通知任务 -> 模板渲染 -> 发送渠道 -> 发送记录
```

例如：

```text
daily_publication_published -> send_daily_email -> render template -> email provider -> delivery log
```

### 13.5 订阅与退订

邮件订阅必须考虑：

- 用户如何订阅？
- 是否需要确认订阅？
- 如何退订？
- 如何记录偏好？
- 邮件发送失败如何处理？
- 是否遵守当地法律和平台规则？

### 13.6 常见坑

第一，在业务流程里直接发送邮件。失败会影响主流程。

第二，没有退订。

第三，没有发送记录。

第四，没有区分交易邮件和营销邮件。

第五，没有频率控制，容易打扰用户。

### 13.7 检查清单

- 通知触发事件是什么？
- 通知是否应该异步发送？
- 使用什么模板？
- 用户是否可以关闭？
- 是否需要退订？
- 是否记录发送状态？
- 是否需要失败重试？

## 14. 通用模式十：SEO、分享与增长

### 14.1 问题

很多网站的长期流量来自搜索和分享。SEO 和分享不是后期装饰，而是内容和页面架构的一部分。

### 14.2 SEO 基础模式

可被搜索引擎收录的页面通常需要：

- 稳定 URL
- 清晰标题
- Meta description
- H1
- 结构化内容
- 内链
- 站点地图
- robots 配置
- canonical URL

内容站尤其需要独立详情页。没有详情页，内容很难长期沉淀。

### 14.3 分享预览模式

社交分享通常依赖：

- Open Graph title
- Open Graph description
- Open Graph image
- Twitter card
- 分享 URL

如果网站依赖社交传播，分享图不是附属物，而是核心资产。

### 14.4 增长入口模式

常见增长入口：

- 搜索引擎
- 社交分享
- 邮件订阅
- 邀请机制
- 广告投放
- 内容聚合
- 第三方平台分发

不同入口对应不同架构重点。

搜索入口要求页面可索引。社交入口要求落地页和分享预览。邮件入口要求订阅、发送和退订。邀请入口要求邀请码、归因和奖励。

### 14.5 常见坑

第一，所有内容都只有一个首页，没有详情页。

第二，URL 不稳定，经常变化。

第三，标题和描述全部一样。

第四，分享图无法被外部平台访问。

第五，不做数据统计，无法知道增长来自哪里。

### 14.6 检查清单

- 核心内容是否有独立 URL？
- URL 是否稳定？
- 是否有 SEO 标题和描述？
- 是否有站点地图？
- 分享图是否公开可访问？
- 分享后的落地页是否清楚？
- 是否记录来源和转化？

## 15. 通用模式十一：数据分析、日志与运营后台

### 15.1 问题

网站上线后，需要知道发生了什么。

面向用户的页面解决使用问题，面向运营的后台解决管理问题，面向工程的日志解决排错问题。

### 15.2 数据分析

常见指标：

- PV
- UV
- 来源
- 转化率
- 注册数
- 付费数
- 留存
- 分享次数
- 搜索关键词
- 热门内容

内容站看阅读和分享。工具站看任务创建和成功率。电商看转化和订单。SaaS 看活跃和留存。

### 15.3 操作日志

后台操作应该记录：

```text
actor_id
action
resource_type
resource_id
before
after
created_at
```

操作日志可以帮助排查误操作，也能支持审计。

### 15.4 系统日志

系统日志关注：

- 错误
- 请求耗时
- 第三方 API 失败
- 队列任务失败
- Webhook 处理结果
- 定时任务执行结果

### 15.5 运营后台

后台常见模块：

- 用户管理
- 内容管理
- 审核队列
- 订单管理
- 文件管理
- 系统配置
- 数据看板
- 任务列表
- 日志查询

后台的设计目标不是漂亮，而是高效、准确、可追踪。

### 15.6 常见坑

第一，没有后台，只能直接改数据库。

第二，没有日志，出错后只能猜。

第三，数据指标和业务目标无关。

第四，后台操作没有权限和审计。

### 15.7 检查清单

- 需要看哪些业务指标？
- 出错时如何定位？
- 管理员操作是否记录？
- 是否有任务失败列表？
- 是否需要数据导出？
- 是否需要系统配置后台？

## 17. 从零设计一个网站的完整流程

这一章给你一套实战流程。以后遇到任何新网站，都可以照着走。

### 17.1 用一句话定义网站

格式：

```text
这是一个帮助 [目标用户] 完成 [核心任务] 的 [网站类型]。
```

例子：

```text
这是一个帮助英语基督徒每天阅读并分享经文的内容型网站。
这是一个帮助设计师压缩图片并下载结果的工具型网站。
这是一个帮助小商家销售手工商品的电商网站。
```

如果一句话说不清，说明产品边界还不清。

### 17.2 列角色

写出所有角色：

```text
游客
注册用户
会员
管理员
编辑
商家
买家
```

然后为每个角色写一句话：

```text
游客：浏览公开内容并分享
管理员：管理内容、审核生成结果、控制发布
```

### 17.3 找核心资源

问自己：这个网站最重要的数据是什么？

写成资源列表：

```text
Verse
ImageGeneration
DailyPublication
AdminUser
```

或者：

```text
Product
Order
Payment
Customer
```

### 17.4 写资源行为矩阵

用表格描述角色和行为。

```text
角色      资源        行为
游客      文章        查看、分享
编辑      文章        创建、编辑、提交审核
管理员    文章        审核、发布、下架
```

这张表会直接变成你的功能清单和权限设计。

### 17.5 写状态流转

为核心资源画状态。

```text
draft -> review_required -> approved -> published
```

如果状态很复杂，先不要写代码。先把状态和动作写清楚。

### 17.6 设计页面结构

前台页面：

```text
首页
列表页
详情页
搜索页
关于页
```

后台页面：

```text
登录
仪表盘
资源列表
资源详情
审核页
设置页
```

页面不是凭感觉加的。每个页面都应该服务某个角色、资源和行为。

### 17.7 设计数据表

先写概念模型，再写数据库表。

概念模型：

```text
一条经文可以有多次图片生成
一天最多有一条正式发布内容
一次发布引用一个经文和一个生成结果
```

数据库表：

```text
verses
image_generations
daily_publications
```

这一步的关键是把业务关系说清楚，而不是急着选字段类型。

### 17.8 区分同步和异步

同步适合：

- 页面读取
- 表单保存
- 小型计算
- 简单查询

异步适合：

- AI 生成
- 文件转换
- 邮件发送
- 支付回调
- 大批量导入
- 定时发布

判断标准很简单：用户是否必须等它马上完成？它是否可能失败？是否需要重试？

### 17.9 选择外部服务

常见外部服务：

- 数据库
- 对象存储
- 邮件服务
- 支付服务
- AI 模型
- 搜索服务
- 分析服务
- CDN

外部服务越多，能力越强，但复杂度也越高。MVP 阶段只接入真正支撑核心价值的服务。

### 17.10 切 MVP

MVP 不是功能少，而是只保留能证明核心价值的闭环。

内容站 MVP：

```text
发布内容 -> 用户阅读 -> 用户分享 -> 内容可被搜索收录
```

工具站 MVP：

```text
用户输入 -> 生成结果 -> 用户拿到结果
```

电商 MVP：

```text
用户看到商品 -> 支付 -> 商家知道要交付什么
```

SaaS MVP：

```text
用户注册 -> 创建核心数据 -> 得到持续价值
```

### 17.11 做风险排序

优先解决最大风险。

常见风险：

- 用户是否真的需要？
- 核心技术是否可行？
- 第三方服务是否稳定？
- 成本是否可控？
- 内容是否能持续生产？
- 支付和权益是否准确？
- 审核和风控是否足够？

不要先做最花哨的页面，先打通最关键的闭环。

## 18. 案例：Bible Daily Verse 的架构拆解

本章用当前项目做完整案例。

### 18.1 一句话定义

```text
这是一个帮助英语基督徒每天阅读、理解并分享一条圣经经文的内容型网站。
```

更完整地说：

```text
Bible Daily Verse 是一个内容型网站，带有 AI 图片生成、文件存储、人工审核和定时发布后台。
```

### 18.2 网站类型

主类型：

```text
内容型网站
```

辅助类型：

```text
AI 生成工具
内部 CMS 后台
自动化发布系统
```

### 18.3 用户角色

```text
游客：阅读今日经文、查看历史归档、打开详情页、分享内容
管理员：登录后台、查看内容库、生成候选、审核图片、批准发布、拒绝或重新生成
系统任务：按日期生成候选、发布已批准内容、存储生成资源
```

### 18.4 核心资源

当前项目中的核心资源可以拆成三类。

第一类是经文内容：

```text
Verse
```

它代表一条可被发布的经文，包括正文、出处、解释、标签和生成提示词。

第二类是图片生成结果：

```text
ImageGeneration
```

它代表某个日期、某条经文、某次生成的图片结果，包括模型、提示词快照、图片 URL、存储位置和生成状态。

第三类是每日发布记录：

```text
DailyPublication
```

它代表某一天最终采用哪条经文和哪次生成结果，以及它是否已批准、已发布、跳过或取消。

这三个资源分开是合理的，因为它们解决不同问题：

```text
Verse 解决内容池问题
ImageGeneration 解决生成版本和素材问题
DailyPublication 解决日期排期和正式发布问题
```

### 18.5 核心流程

当前网站的核心流程是：

```text
选择经文 -> 生成图片 -> 上传存储 -> 保存生成记录 -> 人工审核 -> 批准发布 -> 前台展示 -> 用户分享
```

如果写成状态流转：

```text
generation: pending -> processing -> review_required -> approved/rejected/failed
publication: scheduled -> approved -> published
```

### 18.6 当前已使用的设计模式

内容管理模式：

```text
经文内容池
每日发布
归档
详情页
```

文件存储模式：

```text
生成图片 -> 上传到本地或 R2 -> 数据库存公开 URL
```

审核工作流模式：

```text
生成候选 -> 管理员审核 -> Approve/Reject/Regenerate
```

定时任务模式：

```text
cron 触发生成明天候选，并发布今天已批准内容
```

SEO 和分享模式：

```text
每条经文有详情页，详情页使用生成图片作为社交预览图
```

管理员后台模式：

```text
后台登录 -> Dashboard -> 内容库 -> 发布审核页
```

### 18.7 当前功能清单

公开侧：

- 今日经文展示
- 经文解释
- 主图展示
- 历史归档
- 经文详情页
- Facebook、X、WhatsApp 分享
- 关于页
- 订阅入口占位

后台侧：

- 管理员登录
- 管理员退出
- 内容库查看
- 生成明天候选
- 按日期查看生成结果
- 审核通过
- 拒绝
- 重新生成
- 查看提示词快照
- 查看发布状态

系统侧：

- AI 图片生成
- SVG 或图片卡片生成
- 本地/R2 存储
- 公开资源 URL 保存
- 定时发布入口
- 数据库状态记录

### 18.8 未来可以补的模式

真实邮件订阅：

```text
Subscriber -> SubscriptionPreference -> DailyEmailJob -> EmailDeliveryLog
```

图片质量审核：

```text
GenerationResult -> QA Check -> review_required/failed -> Admin Review
```

搜索和筛选：

```text
按经文出处、主题标签、关键词搜索归档
```

运营数据：

```text
阅读量、分享点击、订阅转化、热门经文
```

广告变现：

```text
广告位配置 -> 页面展示 -> 点击统计 -> 收益分析
```

用户收藏：

```text
User -> FavoriteVerse
```

但这些都不是第一优先级。当前网站最核心的闭环仍然是：

```text
每日内容稳定生成 -> 审核 -> 发布 -> 分享传播
```

### 18.9 当前架构评价

这个项目已经不是一个简单静态内容页，而是一个轻量内容发布系统。

它的架构亮点是：

- 内容、生成结果、每日发布三类资源分离清楚
- 生成结果支持版本
- 发布记录独立于经文本身
- 文件存储可以在本地和 R2 之间切换
- 后台审核把 AI 生成的不确定性挡在正式发布之前
- 详情页和分享图服务传播目标

它接下来最值得优先加强的是：

- 生成图片的质量验证
- 订阅入口从占位变成真实邮件系统
- 发布和生成失败时的后台可见性
- 归档页搜索或主题筛选
- 基础访问和分享统计

```text
要展示文章 -> 内容管理模式
要上传图片 -> 文件上传与对象存储模式
要让用户登录 -> 身份与权限模式
要管理员审核 -> 状态机与审核工作流模式
要生成图片 -> AI 生成任务模式
要处理大文件 -> 异步任务与队列模式
要用户搜索 -> 搜索与筛选模式
要收钱 -> 支付、订阅与权益模式
要发邮件 -> 通知与订阅模式
要被搜索引擎收录 -> SEO 模式
要被社交平台传播 -> 分享预览模式
要知道效果 -> 数据分析与日志模式
```

### 19.3 数据表设计清单

为每个核心资源检查：

- 是否有 id？
- 是否有 owner_id？
- 是否有 status？
- 是否有 created_at 和 updated_at？
- 是否需要 deleted_at？
- 是否需要 slug？
- 是否需要 published_at？
- 是否需要 created_by 和 updated_by？
- 是否需要版本？
- 是否需要关联文件？
- 是否需要操作日志？

### 19.4 页面设计清单

为每个角色检查：

- 进入网站的第一个页面是什么？
- 主要任务从哪里开始？
- 完成任务需要几个步骤？
- 成功后看到什么？
- 失败后看到什么？
- 空数据时看到什么？
- 是否需要详情页？
- 是否需要列表页？
- 是否需要后台页？
- 是否需要设置页？

### 19.5 后台设计清单

后台通常需要：

- 登录
- 仪表盘
- 资源列表
- 搜索筛选
- 详情查看
- 编辑
- 状态操作
- 批量操作
- 审核队列
- 任务列表
- 系统配置
- 操作日志

### 19.6 异步任务清单

只要一个动作符合下面任一条件，就考虑异步：

- 超过几秒
- 调用第三方
- 容易失败
- 需要重试
- 可以稍后完成
- 需要批量执行
- 需要定时执行

任务设计时检查：

- 任务状态
- 输入参数
- 输出结果
- 错误信息
- 重试次数
- 开始时间
- 完成时间
- 是否幂等

### 19.7 MVP 切分清单

问自己：

- 没有这个功能，核心价值还能成立吗？
- 这个功能服务主流程还是支线？
- 这个功能是为了真实用户，还是为了想象中的完整性？
- 这个功能以后加会不会很难？
- 这个功能现在做会不会拖慢验证？

MVP 要保留的是闭环，不是功能数量。

## 结语

做网站不是把页面拼起来，也不是把流行技术栈堆起来。真正的网站架构能力，是看见页面背后的角色、资源、行为、状态、权限和流程。

你之后可以把任何网站都拆成三层：

```text
第一层：它是哪种网站类型？
第二层：它由哪些通用功能模式组成？
第三层：每个模式在当前业务里应该选择哪种实现方案？
```

当你掌握这三层，你就能从“我要做一个网站”走向“我要设计一个系统”。这也是从页面开发者走向产品架构者的关键一步。
