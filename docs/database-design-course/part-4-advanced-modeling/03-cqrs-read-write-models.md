# 03. CQRS 和读写模型分离

CQRS 是 Command Query Responsibility Segregation，命令和查询职责分离。

简单说：

- 写模型服务业务规则和一致性
- 读模型服务页面查询和性能

## 为什么需要 CQRS

有些系统写入模型很规范，但读取页面需要复杂聚合。

例如社交 feed：

- 用户关系
- 动态事件
- 评论数
- 点赞数
- 作者资料
- 可见性权限

每次实时 join 可能很慢。这时可以维护读模型。

## 写模型

写模型保持规范化和约束。

```text
posts
comments
likes
follows
```

它负责正确性。

## 读模型

读模型按页面组织。

```text
feed_items
- user_id
- actor_name
- post_title
- comment_count
- like_count
- created_at
```

它负责快速读取。

## 同步方式

- 同事务更新：一致性强，写入更慢
- 异步更新：写入快，读模型可能延迟
- 定时重建：简单，但不实时
- 事件驱动：灵活，但系统复杂

## 代价

CQRS 会带来：

- 更多表
- 同步逻辑
- 一致性问题
- 重建机制
- 调试难度

早期不要过度使用。先用规范模型和普通查询，遇到明确读性能问题再引入读模型。

## 本章原则

> 写模型优先保证事实正确，读模型服务复杂读取；只有当查询复杂度或性能真的需要时，再把两者分离。
