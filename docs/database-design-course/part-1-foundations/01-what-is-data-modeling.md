# 01. 什么是数据建模

数据建模是把业务世界翻译成数据结构的过程。

前端工程师习惯从页面和组件出发：这个页面需要什么字段，这个组件需要什么 props，这个 API 返回什么 JSON。但数据库设计的出发点不同。数据库不是页面字段的收纳箱，而是系统长期承认的事实、对象、关系、过程和规则。

一个好的数据模型应该能回答：

- 系统里有哪些长期存在的东西？
- 哪些事情发生过，需要记录？
- 哪些状态会变化？
- 哪些关系必须合法？
- 哪些规则永远不能被打破？
- 哪些数据需要代表历史，而不是当前值？
- 哪些查询是产品最重要的读取路径？

## 数据模型和 UI 模型不同

UI 模型通常为了渲染方便而组合数据。

```ts
type TodayVerseCard = {
  publishDate: string;
  referenceText: string;
  verseText: string;
  imageUrl: string;
  shareUrl: string;
}
```

这个对象很适合组件，但不一定适合直接建成一张表。它可能来自多个事实：

- `publishDate` 来自发布记录
- `referenceText` 和 `verseText` 来自内容库
- `imageUrl` 来自生成记录
- `shareUrl` 由路由规则计算出来

前端模型经常是“为了展示而拼出来的结果”。数据库模型应该表达“这些结果背后的事实源”。

## 数据库设计的四类材料

你可以先把数据分成四类。

### 1. 实体

实体是业务里有独立身份的对象。

例子：

- 用户
- 商品
- 订单
- 文章
- 经文
- 团队
- 发票

实体通常会成为表，并有自己的主键。

### 2. 关系

关系描述实体之间如何连接。

例子：

- 一个用户写多篇文章
- 一个订单包含多个商品
- 一个团队有多个成员
- 一条经文可以生成多张图片

关系决定外键和中间表。

### 3. 事件或过程

事件是发生过的动作，过程是可能持续一段时间的任务或工作流。

例子：

- 用户登录了一次
- 支付 provider 发来一个 webhook
- 管理员审核通过
- AI 生成任务失败
- 商品库存发生扣减

这类数据通常需要时间戳、状态、触发者、失败原因和上下文。

### 4. 规则

规则定义什么数据不允许出现。

例子：

- 邮箱不能重复
- 订单必须有用户
- 同一团队里一个用户只能出现一次
- 同一天只能发布一条正式内容
- 金额不能为负

重要规则应该尽量用数据库约束表达，而不是只靠代码判断。

## 数据模型是产品判断的沉淀

数据库 schema 经常暴露产品是否想清楚。

比如“发布内容”这个概念，可能有几种模型：

```text
文章表上有 published_at
```

这适合简单博客。

```text
文章版本表 + published_version_id
```

这适合需要保留版本的 CMS。

```text
发布记录表，指向内容和资产
```

这适合按日期排期、需要审核、候选可替换的内容系统。

不同 schema 背后是不同产品规则。建模不是纯技术，它是在帮产品确定事实边界。

## 建模时要从变化原因出发

一个很实用的判断原则：

> 如果两个字段变化原因不同，它们可能不应该住在同一张表里。

例如：

- 用户名变化是账号资料问题
- session 过期是登录状态问题
- 订单状态变化是履约流程问题
- 商品价格变化是价格策略问题
- 历史订单金额不能变化是财务记录问题

变化原因不同，生命周期往往不同。生命周期不同，就可能需要拆表或保存快照。

## 好模型的几个特征

一个好数据模型通常有这些特征：

- 每张表的职责能用一句话说清楚
- 外键关系和业务关系一致
- 重要规则有约束兜底
- 状态字段有清晰生命周期
- 历史数据不会被当前值污染
- 高频查询路径清楚
- 未来扩展有方向，但没有过度抽象

反过来，如果一张表里同时塞了内容、任务、审核、发布、统计、权限，就很可能是在用一张表承担多个生命周期。

## 本章原则

本章只需要记住一句话：

> 数据建模是把业务事实、关系、过程和规则翻译成稳定结构，而不是把页面字段搬进数据库。
