# 04. 规范化和反规范化

规范化和反规范化不是互相敌对的口号，而是两种服务不同目标的工具。

- 规范化：让事实只有一个归属，减少不一致
- 反规范化：为了历史、性能或读取方便，故意保存重复

关键问题不是“能不能重复”，而是：

> 这份重复数据是错误的冗余，还是有明确语义的快照或读模型？

## 规范化解决什么问题

规范化主要防止三种异常。

### 更新异常

同一个事实存了多份，改一处漏一处。

例如作者名称存进每篇文章。作者改名时，要更新所有文章。

### 插入异常

想创建一个对象，却被迫提供不相关数据。

例如没有文章就无法创建作者。

### 删除异常

删除一条记录时，意外丢失另一类事实。

例如删除作者最后一篇文章后，作者信息也没了。

## 常见范式的直觉

你不一定要背范式定义，但要理解直觉。

### 第一范式

字段应该是可理解的单值，不要在一个字段里塞混乱列表。

坏例子：

```text
tags = "database,postgres,orm"
```

如果标签需要查询和管理，应拆表。

### 第二范式

字段应该依赖整条记录的身份，而不是只依赖组合主键的一部分。

订单明细里的商品名快照依赖这条明细，商品当前名称依赖商品本身。

### 第三范式

非主键字段不要依赖另一个非主键字段。

例如订单表里存 `user_email`，如果它只是用户当前邮箱，就应该通过 `user_id` 关联用户表。

## 什么时候拆表

满足这些条件时，考虑拆表：

- 字段变化原因不同
- 生命周期不同
- 权限不同
- 查询频率差异巨大
- 可能从一个变多个
- 需要独立引用
- 需要独立历史

例子：

- 用户和 session 拆开
- 订单和订单明细拆开
- 文章和文章版本拆开
- 商品和价格历史拆开
- 内容和发布记录拆开

## 反规范化的合理理由

### 历史快照

订单需要保存下单时价格。

```text
order_items.unit_price_snapshot
```

这是正确重复，因为历史订单不能随商品当前价格变化。

### 读取性能

高流量页面可能需要读模型。

```text
feed_items
```

它从多个事实表投影而来，服务快速读取。

### 外部证据

发票、合同、邮件、支付回执通常需要保存生成时内容。

即使用户资料后来修改，历史凭证也不能变。

## 反规范化的代价

保存重复意味着要回答：

- 谁负责更新重复数据？
- 源数据和重复数据不一致时，谁是真相？
- 重复数据能否重建？
- 重复数据是否需要事务保证同步？

如果答不清楚，就不要反规范化。

## JSON 字段

Postgres 的 `jsonb` 很有用，但不能替代建模。

适合 JSON：

- provider 原始响应
- 灵活 metadata
- 展示配置
- 很少过滤的附加信息

不适合 JSON：

- 需要 join 的关系
- 需要唯一约束的字段
- 高频 where 和 order by
- 重要业务状态

JSON 适合表达“边界不稳定的数据”，不适合隐藏核心模型。

## 本章原则

> 规范化让事实归属清楚；反规范化必须说明它是快照、投影还是性能优化，并明确哪份数据是真相。
