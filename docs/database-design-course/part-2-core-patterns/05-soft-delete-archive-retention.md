# 05. 软删除、归档和保留策略

删除不是一个简单动作。不同数据有不同删除语义。

常见选择：

- 物理删除
- 软删除
- 归档
- 匿名化
- 保留到期后删除

## 物理删除

直接从数据库删除。

适合：

- session
- 临时任务
- 缓存
- 可重建数据
- 测试数据

不适合：

- 订单
- 发票
- 支付记录
- 审核记录
- 用户生成的重要内容

## 软删除

软删除常用字段：

```text
deleted_at
deleted_by
```

`deleted_at is null` 表示未删除。

优点：

- 可以恢复
- 保留历史
- 不破坏引用

缺点：

- 所有查询都要过滤
- 唯一约束变复杂
- 数据越积越多
- 权限和隐私语义更复杂

## 归档

归档表示数据不再活跃，但仍可查。

```text
status = archived
archived_at
```

适合：

- 已结束项目
- 已发布旧版本
- 过期内容
- 历史配置

归档不是删除。归档数据通常仍可用于报表和历史展示。

## 保留策略

保留策略回答：数据应该保存多久？

例子：

- session 保存 14 天
- audit log 保存 1 年
- 财务记录保存 7 年
- 用户请求删除后 30 天内清除个人数据

可以设计：

```text
retention_expires_at
purged_at
```

或用定时任务按表清理。

## 匿名化

有些数据不能删除业务记录，但可以清除个人身份信息。

例如订单要保留财务记录，但用户请求删除账号后，可以匿名化：

```text
customer_email = null
customer_name = "Deleted user"
```

这涉及合规和产品政策，不能只从技术角度决定。

## 唯一约束和软删除

软删除会影响唯一约束。

如果 `users.email unique`，用户软删除后，新用户还能否使用同一邮箱？

可以用条件唯一：

```text
unique(email) where deleted_at is null
```

这表示未删除用户邮箱唯一。

## 常见反模式

- 所有表无脑加 `deleted_at`
- 查询忘记过滤 deleted 数据
- 软删除了父记录，却没有处理子记录
- 以为软删除满足隐私删除要求
- 归档、删除、禁用三个概念混用

## 本章原则

> 删除是一种业务语义；物理删除、软删除、归档、匿名化和保留策略要按数据价值、恢复需求和合规要求分别设计。
