## Part 1 · Foundations

### Q：如何更好地理解"实体"这个概念？

> 来自：`01-what-is-data-modeling.md`

**问题背景**

在汉语中，提到"实体"通常会想到一个看得见摸得着的东西，比如用户、商品。但"订单"没有物理对应，这让"实体"的概念不够直观。

---

**解答**

"实体"在数据建模里的定义比日常汉语更窄、更精确：

> **实体是业务里有独立身份的对象。**

关键词是**"独立身份"**，不是"物理存在"。

**判断一个东西是否是实体，问三个问题：**

1. **它在业务里有没有唯一的 ID？**
   订单有订单号，用户有用户 ID，商品有商品编码。只要业务需要区分"这一个"和"那一个"，它就有身份。

2. **它有没有自己独立的属性和生命周期？**
   订单有创建时间、金额、状态（待付款 → 已付款 → 已完成 → 已退款），其状态变化独立于用户和商品。

3. **它会不会被其他东西引用？**
   支付记录、物流信息都会说"我属于哪个订单"。能被引用，说明它是一个独立存在的对象。

**订单为什么是实体而不是事件？**

订单是持续存在的业务对象，状态会随时间演变，可以被修改、查询、关联其他记录。相比之下，"用户支付了一次"是事件——那次支付行为是事件，订单本身是实体。

**更直观的理解框架：**

> **实体是业务对话里的"名词主语"，你可以对它说"给我查一下这个 XXX"。**

- 给我查一下这个**用户**的信息 → 用户是实体
- 给我查一下这个**订单**的状态 → 订单是实体
- 给我查一下这张**发票**的金额 → 发票是实体
- "用户登录了一次" → 不是实体，是事件；你查的是登录日志

这个框架适用于所有抽象实体，包括"订单"、"发票"、"合同"这类纯业务概念。

### Q：在 bible-verse 项目里，"发布内容"用的是哪个模型？这个模型如何记录"产生→拒绝→产生→审批通过并发布"的完整流程？

> 来自：`01-what-is-data-modeling.md`

**解答**

项目使用的是第三种模型：**发布记录表，指向内容和资产**，对应 schema 里的三张核心表：

- `verses` — 经文内容（长期存在的实体）
- `image_generations` — 每一次图片生成的记录（过程）
- `daily_publications` — 最终的发布记录（指向某条经文 + 某次生成结果）

**完整流程的数据状态（以 2026-05-09 为例）：**

1. **第一次产生**：在 `image_generations` 里插入一行，`generationVersion: 1`，`status: pending → processing → review_required`，`triggerType: cron`。

2. **管理员拒绝**：`image_generations` 该行 `status` 更新为 `rejected`。如果已有 `daily_publications` 行指向它，那行变为 `cancelled`。

3. **第二次产生**：再插入一行 `image_generations`，`generationVersion: 2`，`status: pending → processing → review_required`，`triggerType: manual_regenerate`。`(targetDate, generationVersion)` 有唯一约束，版本号不会重复。

4. **审批通过并发布**：`image_generations` gen-002 的 `status` 更新为 `approved`，同时在 `daily_publications` 插入一行：`generationId → gen-002`，`status: approved → published`，`approvedBy`、`approvedAt`、`publishedAt` 依次填入。`daily_publications` 有条件唯一约束，保证同一天不能有两条 `approved` 或 `published` 的记录。

**为什么用这个模型而不是另外两种：**

| 模型 | 问题 |
|---|---|
| `published_at` 字段 | 无法表达"内容+图片分开生成、图片可以重新生成"的结构 |
| 版本表 + `published_version_id` | 内容（verse）相对稳定，变化的是图片生成过程，不匹配 |
| **发布记录表（本项目）** | 完全匹配：按日期排期、需要审核、图片可重新生成 |

`daily_publications` 这张表的职责可以用一句话说清楚："哪一天，用哪条经文，配哪张图，谁批准的，什么时候发出去的"。

### Q：事件或过程这类材料需要单独建一张表吗？

> 来自：`01-what-is-data-modeling.md`

**解答**

不一定，要看这个事件是否需要被独立查询、审计或关联。有三种处理方式：

1. **不建表，只更新状态字段**：适合简单、一次性、不需要历史的动作。比如"用户激活了账号"，只需在 `users` 表加 `activated_at` 字段即可。

2. **建独立表，记录事件本身**：适合需要审计、需要知道发生了多少次、失败原因是什么的场景。项目里的 `image_generations` 就是这种，每次图片生成都是独立事件，记录了版本、触发者、状态、失败原因等。

3. **建独立表，但只记录关键节点**：适合过程很长但中间状态不重要的场景。

**判断要不要单独建表的核心问题：**

> 你以后会不会需要查这个事件本身，而不只是查它的结果？

| 问题 | 答案是"是" → 建表 | 答案是"否" → 不需要 |
|---|---|---|
| 需要知道发生了几次吗？ | 用户登录次数、生成重试次数 | 账号激活（只需知道有没有） |
| 需要知道失败原因吗？ | 生成失败、支付失败 | 简单的状态切换 |
| 需要关联到其他记录吗？ | 这次生成对应哪个发布记录 | 孤立的状态更新 |
| 需要审计谁操作的吗？ | 管理员审批、审核操作 | 系统自动完成的简单任务 |

### Q：如果一开始用简单方式建表，后来需要事件历史时，过往数据岂不是丢失了？要不要一开始就按复杂情况建表？

> 来自：`01-what-is-data-modeling.md`

**解答**

这是一个真实存在的工程矛盾。但"早建"还是"晚建"不是核心问题，核心问题只有一个：

> **这个数据如果现在不记录，以后能补回来吗？**

- **不能补回来** → 现在就记录（哪怕结构简单）
- **能补回来** → 等真正需要时再建

"过早优化"说的是不要过早建复杂的**查询结构和索引**，但从来不是说可以不记录**无法复原的原始事实**。

一个折中方案：**先记录事件（append-only），但不急着建查询接口或专门的结构。** 这样历史数据不会丢，等真正需要查的时候，数据都在，再建索引、建视图甚至迁移到新表。

项目里的 `image_generations` 就是这个思路——每次生成只插入新行，不修改旧行，历史数据永远保留。

### Q：识别实体的那些问题是"或"的关系吗？用户和商品价格历史有生命周期吗？

> 来自：`02-entities-attributes-relationships.md`

**解答**

这些问题是**"或"的关系**——满足其中一条就足以让它成为实体。但更准确的说法是：这些问题是从不同角度**验证同一件事**，现实中真正的实体往往会满足多条。

**用户有生命周期吗？**

有。用户会被注册、被激活、被封号、被注销。它也满足其他所有条件：需要单独创建/删除、会被订单和评论引用、需要列表和权限管理、会出现多条记录。用户是实体，这五条几乎全部命中。

**商品价格历史有生命周期吗？**

它的生命周期很"浅"：通常只有创建（记录一次价格变动），很少被修改，不会被删除（历史记录要保留）。如果只看"生命周期"这一条，它看起来并不典型。但它仍然是实体，因为它满足其他条件：会出现多条记录、会被其他数据引用（订单快照、价格对比）、需要列表和统计（价格趋势图）。

**实用判断方式：** 只要有一到两条命中，就认真考虑建表；如果一条都不满足，通常应该是字段而不是表。

### Q：订单、商品、订单明细是三个实体吗？

> 来自：`02-entities-attributes-relationships.md`

**解答**

是的，这三个都是实体，但角色不同：

- **订单（Order）**：独立存在，有完整生命周期：创建 → 支付 → 发货 → 完成/取消。
- **商品（Product）**：独立存在，完全独立于任何订单，有自己的上架、改价、下架流程。
- **订单明细（Order Item）**：也是实体，但是**关系实体**——连接订单和商品，同时附带额外信息（数量、成交价格、SKU 快照等）。

**为什么订单明细不能只是订单的一个 JSON 字段：**

用 JSON 数组存 items 会失去：对单个明细的查询能力（哪些订单买过商品 X）、对数量和价格的单独统计、对每条明细的独立状态追踪（部分退款、部分发货）。

```
orders       (id, user_id, status, created_at)
products     (id, name, price, ...)
order_items  (id, order_id, product_id, quantity, unit_price_snapshot)
```

`unit_price_snapshot` 是关键——它冻结下单时的价格，商品改价不影响历史订单金额。

### Q：级联删除订单和订单明细，是否真的需要物理删除订单？

> 来自：`02-entities-attributes-relationships.md`

**解答**

大多数业务系统里，订单不会被物理删除。用 `status = 'cancelled'` 或 `deleted_at` 标记是标准做法，原因是：财务对账需要历史记录、用户需要查看历史订单、数据分析依赖完整数据、监管合规要求保留交易记录。

如果订单从不物理删除，**级联删除这个问题根本不会出现**，不需要考虑。

但软删除并不等于"不存在删除场景"，只是把删除从数据库操作变成了状态变更。仍然需要考虑：

- 订单被取消后，`order_items` 的状态要不要同步更新？
- 查询订单列表时，要不要过滤掉已删除的订单及其明细？
- 如果某天真的需要清理 N 年前的历史数据，物理删除时级联关系还是存在的

| 场景 | 处理方式 |
|------|---------|
| 订单取消 | `orders.status = 'cancelled'`，order_items 不动或同步标记 |
| 数据归档清理 | 才涉及物理删除，此时需要考虑级联关系 |
| 误操作恢复 | 软删除可以撤销，物理删除不能 |

课程里提到级联删除，主要是解释**外键约束的机制**，而不是说实际业务里订单应该被删。
