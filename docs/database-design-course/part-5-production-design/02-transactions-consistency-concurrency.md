# 02. 事务、一致性和并发

数据库设计不能只考虑单个请求。生产系统会有并发、重试和部分失败。

事务用来保证一组写入要么都成功，要么都失败。

## 什么时候需要事务

只要一个业务动作要写多张表，就考虑事务。

例子：

- 创建订单和订单明细
- 支付成功后更新订单和插入支付事件
- 写库存流水并更新库存余额
- 审核通过并替换当前发布版本

## 原子性

如果创建订单时：

1. 写入 orders 成功
2. 写入 order_items 失败

就会出现半条订单。

事务可以让它们一起回滚。

## 并发问题

常见并发问题：

- 两个请求同时创建 active subscription
- 两个 worker 抢同一个 job
- 两个用户同时购买最后一件库存
- cron 重复触发生成任务

解决方式：

- 唯一约束
- 行锁
- 乐观锁版本号
- 事务隔离级别
- 幂等 key

## 乐观锁

表上加版本号：

```text
version integer
```

更新时：

```text
where id = ? and version = old_version
```

如果影响 0 行，说明被别人改过。

适合冲突不频繁的编辑场景。

## 行锁

库存扣减、job claim 这类场景可能需要锁住行。

```text
select ... for update
```

锁能保证一致性，但也会降低并发。只锁必要范围。

## 本章原则

> 任何跨表写入、余额变化、唯一业务结果和 worker 抢占，都要考虑事务和并发保护。
