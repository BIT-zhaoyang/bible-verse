# 数据库设计课程写作手册

面向前端工程师的数据库设计课程。目标不是讲语法，而是帮读者建立建模直觉——知道什么时候该用某个机制、为什么不用会出问题、用了之后要注意什么。

重写或扩写章节时，先读这份手册。

---

## 一、书级编写规则

写每一章之前，先想清楚这一章在整本书里的位置。

### 全书的三层结构

```
Part 1       建模语言       教读者用什么词汇和工具思考
Part 2-4     建模模式       教读者识别和使用反复出现的设计方案
Part 5-6     生产和综合      教读者把模式用到真实系统，并做自我评审
```

这个层次决定了每一章允许假设读者已经知道什么，以及每一章需要解释到什么深度。

### 管理读者的已知状态

**每章只能假设读者已经读完它之前的所有章节。**

写一章之前，要主动列出：这一章用到了哪些概念？这些概念在哪一章引入的？如果某个概念还没有被引入，有两种处理方式：

- **如果这个概念简单**：在本章第一次使用时一句话带过，并注明后面哪章会详细讲。
- **如果这个概念复杂**：不要在这里顺带解释，把这一章的依赖前移，或者在 README 的章节顺序里调整。

不要让读者带着"这个词我没见过"的疑问继续读。

### 跨章引用的写法

**向后引用**（引用前面已讲过的概念）：简短点名，不重复解释。

```text
如第三章所讲，外键保证引用的行真实存在。这里我们假设 order_items.order_id 已经声明了外键约束。
```

**向前引用**（提到后面才会详细讲的概念）：一句话点到为止，并告诉读者在哪里能找到详细内容。

```text
这里我们只讨论物理删除。软删除的设计模式在 Part 2 第五章单独讲。
```

不要在一章里预先讲太多后面章节的内容。读者会在正确的时机遇到它。

### 统一例子域

**全书使用同一组业务域的例子**，不要在每章里随意换场景。这样读者可以在不同章节之间建立联系，看到同一个业务域是怎么被一层一层完善的。

主要例子域：

- **电商**：users / products / orders / order_items / payments（覆盖范围最广，几乎每个模式都能用）
- **内容发布**：articles / publications / drafts（CMS、版本、状态机）
- **SaaS**：teams / memberships / subscriptions（多租户、权限、账单）
- **Bible Daily Verse**：verses / images / generation_jobs（AI 生成、内容工作流，贯穿案例）

**选例子的优先顺序**：先用电商，因为前端工程师最熟悉。需要展示电商覆盖不了的特性时，再换到其他域。

每个域内的字段名要保持一致。例如所有表的主键都叫 `id`，时间字段统一用 `created_at` / `updated_at` / `deleted_at`，状态字段统一叫 `status`。

### Part 级叙事弧

每个 Part 的第一章要交代这个 Part 要解决什么问题、和上一个 Part 是什么关系。不要让 Part 只是一个章节列表，要让它有自己的起点和终点。

每个 Part 最后一章（或者结尾）要做一个回顾：这个 Part 的几个概念之间是什么关系，读者现在具备了什么新的判断能力。

### 难度曲线

Part 1 的每一章都面向从未认真设计过 schema 的前端工程师。不假设读者知道什么是范式、什么是事务、什么是索引。

Part 2 开始可以假设读者已经掌握 Part 1 的全部内容，直接用 Part 1 的词汇，不再解释基本概念。

Part 3 可以假设读者对模式已有认知，重点放在"这个领域的特殊挑战是什么"以及"如何用已知模式组合解决"。

Part 4-5 面向有一定实践经验的读者，可以引入更多权衡和边界条件，不需要从头建立动机。

## 二、单章编写规则

### 核心框架：六个叙事维度

每个知识点可以从六个维度展开。**不需要每次全部用上**，但写之前要主动判断哪几个维度是这个知识点必须覆盖的。

```
What     →  这个机制是什么
Why      →  不用它会出什么问题（用反面场景驱动）
How      →  怎么写（按使用场景分块，不按语法分块）
When     →  有多个选项时，什么条件下选哪个
Caveat   →  用了之后有什么容易误用或误解的地方
Boundary →  这个默认原则在哪里失效
```

简单概念通常只需要 What / Why / How。复杂概念、有多个选项的概念，才需要展开 When / Caveat / Boundary。

---

### 每个维度怎么写

### What

一两句话说清楚这个机制做什么。不要用另一个同等陌生的术语来定义它。

### Why

**用反面场景驱动，不用优点列举。**

固定模式：
1. 演示不用这个机制时，出什么具体的业务问题（给出真实数据样本或场景）
2. 追问这个问题为什么会发生
3. 说明这个问题的后果
4. 最后说这个机制如何解决

好的 Why 是一个小型故障分析。不是"这个机制的好处是……"，而是"如果没有它，你的业务会这样坏掉"。

### How

**按使用场景分块，不按语法分块。**

同一个机制往往有多种写法。不要按"写法一、写法二"组织，而是按"这种情况用这种写法"组织。每种写法后面紧跟它适合的场景，以及关键的细节或注意点。

如果涉及数据库操作，尽量同时给出 SQL 和对应的 TypeScript/ORM 代码，把数据库概念和前端工程师实际写的代码直接连起来。

### When

**用表格呈现，列是判断条件，行是选项。**

When 回答的是：有多个合法写法或策略时，如何根据业务条件做选择。表格之后要有一两句文字给出默认结论，不要让读者自己从表格里推导。

### Caveat

**紧贴在相关知识点之后，不要集中到节尾。**

Caveat 回答"用了之后有什么容易踩的坑"。它不否定主结论，而是在读者已经决定"用这个"之后，补充一个容易出错的细节。

写 Caveat 的原则：短、准、不引出太深的支线。一两句话，紧跟在刚讲完的那个知识点后面。

### Boundary

**给默认原则，再补边界条件。**

Boundary 回答"这个原则在什么情况下不成立"。教学文章容易把默认建议写成绝对规则，Boundary 是防止这件事发生的机制。

写法模式：

- 不写"任何一张表都需要主键"
- 改成"几乎所有业务表都应该有主键；纯关联表也应该有组合主键或组合唯一约束"

---

### 章节结构

### 开头：锚定上下文，给读者一张地图

开头一句话接上前一章，然后列出本章要解决的问题或要串起来的概念。

好的开头不是定义堆叠，而是让读者在读第一段时就知道全章的结构。

示例模式：
```text
前两章讲了如何识别实体、属性和关系。这一章讲如何把这些设计决策落实到表结构里。
```

### 结尾：沉淀一句可迁移的原则

结尾不只是总结内容，而是给一个读者以后设计 schema 时脑子里会浮现的判断句。

示例：
```text
数据库不只是存储数据，也应该帮你验证身份、引用和不可破坏的业务规则。
```

### 章末延伸：处理自然产生的疑问

如果一章讲完之后，读者很可能产生一个延伸疑问，直接在章末回答它。不要让读者带着疑问离开。

例如第三节讲完约束之后，自然会有人问"那业务逻辑到底该放数据库还是应用层"，这个问题直接在章末展开。

---

### 标题层级规则

```
##    独立概念（主键、外键、唯一约束……）
###   该概念的叙事维度（What / Why / How）或子主题
####  同一个 How 里的不同选项（cascade / set null / restrict）
```

---

### 语言风格

**避免教科书腔。** 课程面向前端工程师，目标是建立直觉，不是传递精确定义。

具体原则：
- 先讲问题，再讲机制
- 用真实业务例子，不用抽象占位符
- 给默认选择，不要把每种情况都列出来让读者自己判断
- 少用术语堆叠
- 代码注释只解释"为什么这样写"，不解释"这行代码做了什么"

**选例子时选争议少的场景。** 例子会塑造读者的默认直觉。选语义稳定、在真实产品里不容易有歧义的场景。

例如讲 `ON DELETE CASCADE` 时，"草稿附件随草稿删除"比"文章删除时评论也删除"更稳妥——后者在真实产品里可能需要软删除或审计追踪。

---

## 三、最终检验标准

读者读完一个小节后，应该能回答：

1. 这个机制是什么？（What）
2. 不用它会出什么具体问题？（Why）
3. 怎么写？（How）
4. 如果有多种选择，我的情况该选哪个？（When）
5. 有什么地方容易搞错？（Caveat）
6. 这个原则什么时候不适用？（Boundary）

不是每个知识点都需要六条全部答上，但如果一个本该有 When 的知识点缺了 When，读者就会带着"我知道怎么写，但不知道什么时候写"的疑问离开。
