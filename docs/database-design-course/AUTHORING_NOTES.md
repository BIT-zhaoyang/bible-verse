# 数据库设计课程写作经验

这份笔记记录课程文章的写作准则。以后重写或扩写其他章节时，优先参考这里。

## 1. 用章节开头建立清晰框架

每章开头先回答：

- 本章接在前一章之后解决什么问题？
- 本章会把哪些概念串起来？
- 读完后读者应该形成什么判断能力？

好的开头不是定义堆叠，而是给读者一张地图。

示例模式：

```text
前两章讲了如何识别实体、属性和关系。这一章讲如何把这些设计决策落实到表结构里。
```

## 2. 优先使用 What / Why / How

基础概念章适合按 What / Why / How 写：

- What：这个概念是什么
- Why：没有它会发生什么问题
- How：实际 schema 或 SQL 怎么表达

这比直接讲语法更适合前端工程师，因为它先建立动机，再进入实现。

## 3. 用业务问题解释数据库机制

不要只说“外键保证引用完整性”。要给出孤儿数据、错误 join、删除策略这类具体后果。

好的解释应该让读者看到：

```text
如果不这样设计，业务会怎样坏掉？
```

数据库概念要尽量落到真实场景：

- 用户邮箱变更
- 订单明细找不到订单
- 商品下架和物理删除不同
- 重复点击导致重复写入
- 历史价格不能被当前价格污染

## 4. 把绝对说法改成可操作判断

教学文章容易为了简洁写得太绝对。更好的方式是给默认原则，再补边界条件。

例子：

- 不写“任何一张表都需要主键”
- 改成“几乎所有业务表都应该有主键；纯关联表也应该有组合主键或组合唯一约束”

- 不写“外键必须加索引”
- 改成“外键字段通常需要索引，尤其是会被 join、按父对象查询，或父表可能被删除/更新时”

原则：既要给初学者清晰默认答案，也要避免制造错误心智模型。

## 5. 保留重要 caveat，但不要打断主线

严谨性要服务理解，不要把文章变成注释大全。

适合补充的 caveat：

- UUID 降低枚举风险，但不能替代鉴权
- PostgreSQL unique 允许多行 NULL
- PostgreSQL check 对 NULL/unknown 的行为需要配合 NOT NULL 理解
- unique constraint 和 unique index 语义接近，但建模时关注点不同

写 caveat 的方式要短、准、贴近当前小节，不要引出太深的支线。

## 6. 区分“正确性机制”和“性能机制”

约束和索引经常一起出现，但职责不同：

- 约束保护数据正确性
- 索引优化查询性能
- 唯一索引是少数同时承担规则和性能的结构

文章里要避免把索引说成“防护层”。更准确的说法是“正确性和性能的职责分工”。

## 7. 用表格总结决策规则

当一个概念有多个选项时，用表格帮助读者做判断。

适合表格化的主题：

- 代理主键 vs 自然主键
- 自增整数 vs UUID
- cascade / set null / restrict
- 应用层验证 vs 数据库约束
- enum vs check

表格不要只是罗列差异，要服务“如何选择”。

## 8. 示例要选择争议少的场景

例子会塑造读者的默认直觉。尽量选语义稳定、争议小的例子。

例如讲 `ON DELETE CASCADE` 时，“草稿附件随草稿删除”比“文章删除时评论也删除”更稳妥。后者在真实产品里可能需要软删除或审计。

## 9. 每章结尾要沉淀一句原则

结尾不要只是总结内容，而要给一个可迁移的判断原则。

示例：

```text
数据库不只是存储数据，也应该帮你验证身份、引用和不可破坏的业务规则。
```

这类句子会成为读者以后设计 schema 时的内在提示。

## 10. 不要为了严谨牺牲“像人话”

课程面向前端工程师，目标是建立建模直觉。文章应避免教科书腔。

好的风格：

- 先讲问题，再讲机制
- 用真实业务例子
- 给默认选择
- 在关键处补边界条件
- 少用术语堆叠

最终标准：

> 读者读完后，不只是知道某个 SQL 语法，而是知道什么时候该用它、为什么不用会坏、用了之后要注意什么。
