# 05. 搜索、筛选、排序和发现

当资源数量变多，用户需要找到目标。搜索系统解决的是发现问题。

## 三层搜索方案

第一层：数据库查询。

适合：

```text
数据量小
筛选简单
后台列表
MVP 阶段
```

第二层：全文搜索引擎。

适合：

```text
文章正文搜索
商品搜索
文档搜索
高亮匹配
拼写容错
```

第三层：推荐和个性化。

适合：

```text
内容流
电商推荐
社区分发
媒体平台
```

## 筛选和排序

常见筛选维度：

```text
分类
标签
状态
作者
日期
价格
评分
地区
文件类型
权限范围
```

常见排序：

```text
最新
最热
相关度
价格
评分
自定义排序
```

## URL 设计

搜索和筛选状态最好放在 URL 里：

```text
/archive?q=hope&tag=faith&page=2
/products?category=shoes&price=50-100&sort=popular
```

这样结果可以刷新、分享、收藏，也利于调试。

## 索引同步

如果使用搜索引擎，要考虑数据库和搜索索引如何同步：

```text
写入数据库 -> 发布事件 -> 更新搜索索引
```

或者：

```text
定时全量同步
增量同步
失败重试
后台重建索引
```

索引同步失败时，要能发现和重试。

## 空结果设计

空结果不是简单显示“没有数据”。好的空结果应该告诉用户：

- 当前筛选条件是什么
- 可以清除哪些筛选
- 可以尝试哪些关键词
- 是否有推荐内容

## 常见坑

第一，数据很少就上复杂搜索引擎，维护成本过高。

第二，筛选状态只存在前端状态里，刷新就丢。

第三，后台搜索和前台搜索混用同一套逻辑，权限泄漏。

第四，索引更新失败没有告警。

第五，没有分页或游标，数据一多页面变慢。

## 决策树

```text
只是后台按状态查？数据库查询。
只是标题和标签搜索？数据库 ILIKE 或全文索引。
需要正文搜索、高亮、容错？搜索引擎。
需要个性化排序？推荐系统或规则引擎。
```

## 决策清单

- 搜索对象是什么？
- 搜索字段有哪些？
- 是否需要全文搜索？
- 是否需要筛选组合？
- 是否需要排序？
- 是否需要分页？
- URL 是否保存搜索状态？
- 是否有空结果页？
- 索引如何同步和重建？
