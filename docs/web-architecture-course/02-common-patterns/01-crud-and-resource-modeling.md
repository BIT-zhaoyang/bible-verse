# 01. 资源 CRUD 与业务对象建模

CRUD 是网站最基础的能力：创建、读取、更新、删除。但真正的难点不是写增删改查，而是判断一个东西是否应该成为资源，以及这个资源未来会如何演进。

## 它解决什么问题

CRUD 模式解决的是：

```text
系统如何管理一个长期存在的业务对象。
```

文章、商品、客户、项目、课程、文件、订单、评论，都可能是资源。

## 什么时候使用

当一个对象满足下面任意条件时，就要考虑资源建模：

- 需要被保存和查询
- 有自己的列表页或详情页
- 会被其他对象引用
- 有创建者或所有者
- 有状态
- 有权限
- 需要统计或审计

## 最小实现

最小资源表通常是：

```text
id
title/name
created_at
updated_at
```

如果资源要展示在公开页面，加：

```text
slug
status
published_at
```

如果资源属于用户或组织，加：

```text
owner_id
workspace_id
created_by
updated_by
```

## 成熟实现

成熟资源通常会拆出更多边界：

```text
主表：保存当前状态
版本表：保存历史版本
事件表：保存关键操作
附件表：保存文件资源
关联表：保存多对多关系
```

例如文章系统：

```text
articles
article_versions
article_tags
media_assets
audit_logs
```

## 删除策略

删除有三种常见方案。

物理删除：直接删除数据库记录。适合临时数据、缓存数据、无审计价值的数据。

软删除：加 `deleted_at`。适合用户数据、业务数据、可能需要恢复的数据。

归档：加 `archived_at` 或状态 `archived`。适合不再活跃但仍要保留历史的资源。

不要把所有删除都做成物理删除。订单、支付、审核记录、发布记录通常不应该真删。

## 页面结构

资源 CRUD 对应的页面通常是：

```text
列表页
详情页
新建页
编辑页
删除确认
空状态
```

后台还会需要：

```text
筛选
排序
批量操作
导入导出
操作日志
状态变更
```

## API 或服务层

不要把 CRUD 理解成简单数据库写入。服务层应该表达业务动作。

不好的命名：

```text
updateArticle
```

更好的命名：

```text
saveDraft
submitForReview
publishArticle
archiveArticle
```

同样是更新数据，但业务含义完全不同。

## 常见坑

第一，把字段当资源。比如把多个文件 URL 全塞在文章表，后续想管理文件尺寸、权限和删除就困难。

第二，没有所有者。后续做权限时不知道资源属于谁。

第三，没有状态。后续加草稿、审核、发布时只能补很多布尔字段。

第四，过度抽象。所有资源都套一个万能表，最后每个字段含义都模糊。

## 决策清单

- 这个对象是否有独立生命周期？
- 是否需要列表和详情？
- 是否会被其他对象引用？
- 是否需要所有者？
- 是否需要状态？
- 是否要软删除？
- 是否需要版本？
- 是否需要操作日志？
- 是否会产生多对多关系？

## 练习

选择一个“在线课程网站”，列出哪些应该是资源，哪些只是字段。至少区分：

- Course
- Lesson
- Teacher
- Student
- Progress
- Certificate
- Cover image
