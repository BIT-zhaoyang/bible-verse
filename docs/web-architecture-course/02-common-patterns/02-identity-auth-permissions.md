# 02. 用户、登录、权限和多租户

身份系统回答“你是谁”，权限系统回答“你能做什么”。很多安全问题来自把这两个问题混为一谈。

## 身份模式

常见身份模式有四种。

无登录：适合纯公开内容站、落地页、一次性工具。

管理员登录：适合公开前台加内部后台，例如内容站、运营后台。

普通用户登录：适合收藏、订单、历史记录、个人数据。

组织/团队登录：适合 SaaS、企业系统、多人协作。

## 会话方案

Cookie Session：

```text
适合服务端渲染网站和传统 Web 应用
服务端容易吊销
浏览器体验自然
```

JWT：

```text
适合前后端分离、移动端、多服务调用
吊销较麻烦
不要在 token 里放敏感数据
```

OAuth/OIDC：

```text
适合第三方登录和企业身份集成
实现复杂度更高
```

Magic Link：

```text
适合低频登录、Newsletter、轻量会员系统
依赖邮件可达性
```

## 权限模型

角色权限：

```text
owner
admin
editor
member
viewer
```

资源所有权：

```text
用户只能访问自己的资源
商家只能管理自己的商品
团队成员只能访问所属 workspace
```

能力权限：

```text
can_manage_billing
can_invite_members
can_publish_content
```

简单系统可以从角色权限开始。复杂系统通常需要角色加资源所有权。

## 多租户模式

SaaS 常见多租户结构：

```text
users
workspaces
memberships
roles
business_resources
```

每条业务数据通常带：

```text
workspace_id
created_by
updated_by
```

所有查询都必须带租户边界。否则用户可能看到其他团队的数据。

## 页面结构

身份和权限相关页面：

```text
登录
注册
忘记密码
邮箱验证
个人设置
团队成员
邀请成员
角色管理
账单权限
管理员后台
```

不是所有网站都需要全部页面。MVP 可以只做管理员登录或普通登录。

## 后端校验

权限必须在服务端校验。

前端隐藏按钮只能改善体验，不能保护数据。每个敏感 action 都应该检查：

```text
是否登录
是否属于该资源
是否有执行该动作的权限
资源当前状态是否允许该动作
```

## 常见坑

第一，登录后就允许所有操作。

第二，后台接口只在前端隐藏入口，没有服务端保护。

第三，多租户查询漏掉 `workspace_id`。

第四，管理员角色过大，没有操作日志。

第五，把权限判断散落在各个组件里，后续难以审计。

## 决策清单

- 网站是否需要普通用户登录？
- 是否只需要管理员登录？
- 是否有团队或组织？
- 资源属于用户还是组织？
- 是否需要邀请机制？
- 是否需要角色分级？
- 敏感操作是否有服务端校验？
- 是否需要操作日志？

为一个小型 CRM SaaS 设计角色：

