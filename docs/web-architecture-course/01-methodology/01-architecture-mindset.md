# 01. 网站不是页面集合

初学者做网站，最容易从页面开始：

```text
首页需要什么
详情页需要什么
后台页需要什么
登录页怎么做
```

页面当然重要。用户最终接触的是页面。但如果只从页面出发，你很容易把数据库设计成页面字段的收纳箱，把接口设计成页面数据的搬运工，把后台设计成一堆临时按钮。

真正的网站架构应该从业务世界开始。

## 页面是结果，不是起点

页面回答的是：

```text
用户在这个场景下需要看到什么、操作什么。
```

架构回答的是：

```text
系统里有哪些对象，它们如何变化，谁能改变它们，哪些规则不能被打破。
```

举个例子。一个文章详情页可能显示：

- 标题
- 作者
- 正文
- 封面图
- 发布时间
- 分享按钮

如果从页面出发，你可能会设计一张 `articles` 表，把这些字段都放进去。

但如果从架构出发，你会继续问：

- 文章是否有草稿？
- 作者是否能修改？
- 是否需要审核？
- 封面图是上传还是生成？
- 发布时间是手动还是定时？
- 下架后 URL 是否还存在？
- 分享图是否和正文封面一样？
- 是否需要保存历史版本？

这些问题决定了数据表、后台、状态机、文件存储和发布流程。

## 网站的三个层次

一个网站可以拆成三个层次。

第一层是体验层：

```text
页面、组件、表单、按钮、导航、交互
```

第二层是业务层：

```text
资源、行为、状态、权限、流程、规则
```

第三层是基础设施层：

```text
数据库、缓存、对象存储、队列、搜索、支付、邮件、CDN
```

很多开发问题来自层次混淆。

比如“点击发布按钮后文章为什么没出现在首页”，表面是页面问题，实际可能是状态机问题。  
比如“图片上传后分享图打不开”，表面是上传问题，实际可能是对象存储公开访问和 CDN 问题。  
比如“用户能看到别人的数据”，表面是接口问题，实际是权限边界问题。

## 架构设计的核心任务

架构设计不是一次性把所有东西设计完。它的核心任务是做出清晰边界。

你至少要划清这些边界：

- 前台和后台的边界
- 公开数据和私有数据的边界
- 用户行为和系统任务的边界
- 当前状态和历史事件的边界
- 业务数据和文件资源的边界
- 同步请求和异步任务的边界
- 核心功能和未来扩展的边界

边界清楚，系统就容易演进。边界混乱，功能越多越难改。

## 一个实用的架构观察法

看任何网站时，不要先看页面漂不漂亮，先看它管理什么东西。

打开一个网站，问：

```text
这里最重要的资源是什么？
谁在创建它？
谁在消费它？
它有哪些状态？
它能被搜索、分享、购买、评论或审核吗？
它的数据从哪里来？
它的生命周期在哪里结束？
```

例如一个菜谱网站：

```text
资源：菜谱
创建者：编辑或用户
消费者：访客
状态：草稿、待审核、已发布、下架
行为：浏览、搜索、收藏、评论、分享
增长：SEO 和社交分享
后台：菜谱管理、分类管理、评论审核
```

只要这样拆，网站就不再是“很多页面”，而是一套资源管理和分发系统。

## 初学者常见误区

### 误区一：先做 UI，再补业务规则

UI 先行不是问题，但如果业务规则完全没想，后续很容易返工。

例如你先做了一个“发布”按钮，后来才发现需要草稿、审核、定时发布、预览和撤回。这个按钮背后其实是一整套工作流。

### 误区二：把后台当成附属功能

很多公开网站看起来很简单，但后台很关键。内容站需要内容后台，电商需要订单后台，工具站需要任务后台，AI 产品需要生成记录后台。

后台不是“有空再做”。只要业务需要运营，后台就是系统的一部分。

### 误区三：数据表跟着页面走

页面会变，业务事实更稳定。数据表应该表达业务事实，而不是完全照搬页面布局。

### 误区四：不区分当前状态和历史过程

`status = approved` 只告诉你现在已批准，不告诉你谁批准、什么时候批准、之前被拒绝过几次。是否需要历史，取决于业务风险。

## 小结

网站不是页面集合，而是资源在角色之间流动的系统。

页面是用户接触系统的窗口。架构是系统内部的秩序。

以后做网站时，先问业务世界是什么，再决定页面怎么呈现。
