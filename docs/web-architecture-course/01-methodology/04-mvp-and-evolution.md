# 04. MVP、演进和架构债

很多初学者会在两个极端之间摇摆。

一种极端是“先做最简单能跑的”，结果数据模型和流程太随意，稍微扩展就崩。

另一种极端是“一开始就做完整架构”，结果花了很久还没有核心闭环。

好的 MVP 设计介于两者之间：

```text
功能范围要小，但核心模型不能乱。
```

## MVP 是最小闭环，不是最少页面

MVP 的重点是闭环。

内容站的闭环：

```text
内容生产 -> 发布 -> 被阅读 -> 被搜索或分享带来新访问
```

工具站的闭环：

```text
用户输入 -> 系统处理 -> 用户拿到结果
```

电商的闭环：

```text
用户看到商品 -> 支付 -> 商家交付 -> 订单完成
```

SaaS 的闭环：

```text
用户注册 -> 创建核心数据 -> 持续使用 -> 愿意付费或留存
```

MVP 可以页面少、后台简陋、自动化少，但不能缺失闭环。

## 什么可以简化

MVP 阶段通常可以简化：

- UI 精细度
- 高级筛选
- 复杂权限
- 多角色协作
- 批量操作
- 高级统计
- 推荐系统
- 自动化营销
- 多语言
- 高级搜索引擎

例如内容站第一版可以没有评论和收藏。工具站第一版可以没有历史记录。SaaS 第一版可以先不做团队工作区。

## 什么不能乱省

有些东西即使第一版也不能随便省，因为后期补会很痛。

### 核心资源边界不能乱

如果业务里有三个生命周期不同的对象，不要为了省事硬塞一张表。

Bible Daily Verse 里，`Verse`、`ImageGeneration`、`DailyPublication` 分开是必要的。因为：

- 经文是内容资产
- 图片生成是一次尝试和版本
- 每日发布是日期排期和正式采用关系

硬塞一张表会让生成、审核、发布互相污染。

### 关键状态不能乱

订单、订阅、审核、任务这些流程必须有清晰状态。

你可以第一版不做状态历史表，但至少要有明确 status 和合法跳转。

### 权限边界不能只靠前端

哪怕后台只有一个管理员，也要服务端校验登录。前端隐藏按钮不是权限。

### 外部服务结果要可追踪

AI、支付、邮件、对象存储这些外部服务会失败。第一版也应该保存错误信息和状态，否则调试会非常痛苦。

## 演进路线：从小系统到成熟系统

一个功能通常会经历四个阶段。

### 阶段一：手工流程

用最少系统支持核心闭环，很多事情人工完成。

例如 Newsletter 初期可以手动写文章、手动发邮件、手动看订阅者。

### 阶段二：半自动流程

系统开始记录状态，后台可以触发动作，但仍有人审核。

例如 AI 图片生成后进入后台审核，管理员批准后再发布。

### 阶段三：自动化流程

稳定流程被自动化，失败时进入人工处理。

例如每天定时生成内容、定时发布、发送邮件、生成报表。

### 阶段四：规模化流程

开始关注性能、成本、监控、权限、审计和扩展。

例如引入队列、缓存、搜索索引、分权限后台、操作日志和告警。

## 架构债是什么

架构债不是“代码写得不漂亮”，而是当前设计没有表达真实业务结构，导致未来每一步都要绕路。

常见架构债：

- 所有资源塞在一张大表
- 没有状态机
- 没有所有者字段
- 没有操作日志
- 文件只存 URL，不存 key 和 provider
- 外部服务调用没有任务记录
- 支付状态只靠前端跳转
- 后台直接改数据库
- 权限逻辑散落各处

有些债可以接受，有些债不要欠。

## 如何判断一个简化是否安全

问五个问题：

```text
这个简化是否破坏核心资源边界？
这个简化是否会产生不可恢复的数据？
这个简化是否影响安全或权限？
这个简化是否让失败不可见？
以后补回来是否需要迁移大量数据？
```

如果答案多次是“是”，这个简化不安全。

## MVP 决策示例

假设你要做一个图片压缩工具。

可以先做：

```text
游客上传一张图片
服务器压缩
返回下载链接
临时文件 24 小时后删除
```

可以暂缓：

```text
账号系统
历史记录
批量压缩
付费套餐
浏览器直传
CDN
```

但最好一开始就考虑：

```text
文件大小限制
文件类型校验
处理任务状态
失败错误信息
临时文件清理
```

这些是稳定性和安全底线。
