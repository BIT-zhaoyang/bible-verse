# 03. 从想法到架构蓝图

这一章讲一个实战流程：如何把一句模糊的网站想法，变成可以开工的架构蓝图。

不要从技术栈开始。技术栈是工具，不是架构。

先从业务故事开始。

## Step 1：一句话定义

用这个格式写：

```text
这是一个帮助 [目标用户] 完成 [核心任务] 的 [网站类型]。
```

例子：

```text
这是一个帮助英语基督徒每天阅读并分享经文的内容型网站。
这是一个帮助用户压缩图片并下载结果的工具型网站。
这是一个帮助小团队管理客户跟进记录的 SaaS 网站。
这是一个帮助创作者发布付费文章并通过邮件触达读者的 Newsletter 网站。
```

如果一句话定义写不清，先不要设计页面。产品边界还没清。

## Step 2：写业务故事

业务故事用自然语言描述系统发生什么。

例如 Bible Daily Verse：

```text
系统维护一个经文内容池。
系统每天为明天选择一条经文。
系统根据经文提示词生成图片。
生成图片被保存到对象存储，并记录公开 URL。
管理员在后台审核生成结果。
管理员批准后，该日期的内容进入待发布状态。
日期到达后，系统把已批准内容发布到前台。
游客可以在首页阅读今日经文，也可以进入归档和详情页。
游客可以把详情页分享到社交平台。
```

这段故事比功能清单更有价值，因为它包含对象、动作、规则和时间。

## Step 3：圈出名词，识别资源

从业务故事里圈名词：

```text
系统
经文内容池
明天
经文
提示词
图片
对象存储
公开 URL
管理员
后台
生成结果
日期
游客
首页
归档
详情页
社交平台
```

不是每个名词都要变成资源。筛选标准是：它是否有独立身份和生命周期？

最终可能得到：

```text
Verse
ImageGeneration
DailyPublication
AdminUser
AdminSession
```

`提示词` 是 `Verse` 或 `ImageGeneration` 的字段。  
`首页` 是入口，不是资源。  
`对象存储` 是外部服务，不是业务资源。  
`日期` 是发布记录的重要字段，但不一定单独成表。

## Step 4：圈出动词，识别行为和流程

动词通常暗示行为、状态变化或任务。

上面的故事里有：

```text
维护
选择
生成
保存
记录
审核
批准
发布
阅读
进入
分享
```

这些动词会变成：

- 后台按钮
- API action
- 定时任务
- 状态跳转
- 操作日志

例如：

```text
generateCandidateForDate
approveGeneration
rejectGeneration
publishApprovedForToday
```

## Step 5：写状态流转

为每个会变化的资源写状态。

图片生成：

```text
pending -> processing -> review_required -> approved
pending -> processing -> failed
review_required -> rejected
approved -> superseded
```

每日发布：

```text
scheduled -> approved -> published
scheduled -> skipped
approved -> cancelled
```

状态流转要回答：

- 初始状态是什么？
- 终态是什么？
- 哪些动作改变状态？
- 谁可以改变状态？
- 变化时要记录什么？

## Step 6：画页面入口

页面入口不是随便列，而是从角色和行为推出来。

公开侧：

```text
首页：游客查看今日内容
归档页：游客浏览历史内容
详情页：游客阅读和分享单条内容
关于页：游客了解网站
订阅页：游客留下邮箱
```

后台侧：

```text
登录页：管理员登录
仪表盘：管理员查看今日和明日状态
内容库：管理员查看经文池
审核页：管理员审核生成结果
发布列表：管理员按日期查看排期
```

页面应该对应任务。如果一个页面不能说清服务哪个角色和哪个任务，它可能不该存在。

## Step 7：推导数据表

从资源和关系推导表。

概念关系：

```text
一条经文可以有多次图片生成
一次图片生成属于一条经文
一天最多有一条正式发布内容
一次发布引用一条经文和一次图片生成
管理员可以批准发布
```

表：

```text
verses
image_generations
daily_publications
admin_users
admin_sessions
```

字段不是一开始凭感觉列，而是由问题推出来：

- 需要公开详情页，所以 `verses.slug`
- 需要避免短期重复，所以 `verses.status`、发布记录和日期
- 需要生成版本，所以 `image_generations.generation_version`
- 需要知道存储位置，所以 `image_generations.storage_provider`
- 需要审核，所以 `daily_publications.approved_by`、`approved_at`

## Step 8：区分同步和异步

同步动作：

```text
读取首页
读取归档
管理员点击批准
管理员登录
```

异步或后台动作：

```text
AI 图片生成
文件上传到对象存储
定时生成明日候选
定时发布今日内容
邮件推送
```

判断一个动作是否应该异步，看四点：

- 是否耗时超过几秒？
- 是否依赖第三方？
- 是否可能失败并需要重试？
- 用户是否必须等待结果？

## Step 9：列外部服务

外部服务包括：

```text
数据库
对象存储
AI 模型
邮件服务
支付服务
搜索服务
分析服务
CDN
```

每接入一个外部服务，都要问：

- 它解决什么核心问题？
- 失败时怎么办？
- 成本如何增长？
- 是否需要降级方案？
- 是否需要保存 provider request id 或错误信息？

## Step 10：切 MVP

最后切 MVP。

MVP 不是最少功能，而是最小闭环。

Bible Daily Verse 的 MVP 闭环：

```text
准备经文 -> 生成图片 -> 审核 -> 发布 -> 展示 -> 分享
```

可以暂缓：

```text
用户收藏
评论
复杂搜索
真实广告系统
多管理员角色
高级统计
```

不能乱省：

```text
每日内容的发布状态
图片公开 URL
详情页
审核流程
```

因为这些直接支撑核心闭环。
